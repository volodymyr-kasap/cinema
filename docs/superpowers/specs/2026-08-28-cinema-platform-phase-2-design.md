## 2. Цель и границы

### Цель

Пользователь выбирает места на карте зала, ставит их на холд, видит таймер
и подтверждает бронь. Одно место не может быть занято дважды — это доказано
тестом, а не утверждением.

### В рамках

- Таблицы `reservations` и `reservation_seats`, миграции, инвариант в индексе.
- `ReservationModule`: создание, чтение, отмена, подтверждение.
- State machine брони с ленивым истечением.
- Занятость мест в `GET /showtimes/:id/seats`.
- Идентификация сессии, владение бронью.
- Конкурентные интеграционные тесты (это основной артефакт под-проекта).
- Второй режим тестового харнесса — очистка усечением вместо отката транзакции.
- SPA: мультивыбор мест, страница брони, таймер, отмена и подтверждение.
- ADR на каждое неочевидное решение.

### Вне рамок

Redis, RabbitMQ, Kafka, ClickHouse, Prometheus, k6, rate limiting, платежи,
`Idempotency-Key`, настоящая аутентификация, таблицы `bookings`, `payments`,
`tickets`. Каждое приходит в своём под-проекте вместе с задачей, которую решает.

Отдельно про две вещи, которые под-проект 1 обещал именно здесь:

- **`Idempotency-Key` — не здесь.** Это раздел 12 `spec.md` и под-проект 4:
  идемпотентность имеет смысл вместе с платежом и воркерами, где повтор стоит
  денег. Двойной клик по кнопке холда сегодня создаёт две брони, и вторая
  проигрывает первой на индексе — поведение честное и предсказуемое.
- **Zustand и React Hook Form — не здесь.** См. раздел 8: задачи, которую они
  решают, не появилось. Обещание под-проекта 1 отменяется в пользу первого
  принципа `spec.md`.

## 3. Схема данных

Две таблицы. Инвариант живёт во второй.

```sql
CREATE TABLE reservations (
  id                 uuid PRIMARY KEY DEFAULT uuidv7(),
  showtime_id        uuid NOT NULL REFERENCES showtimes(id),
  session_id         uuid NOT NULL,
  status             text NOT NULL,
  total_price_cents  integer NOT NULL,
  expires_at         timestamptz NOT NULL,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),
  confirmed_at       timestamptz,
  cancelled_at       timestamptz,
  CONSTRAINT reservations_status_check
    CHECK (status IN ('PENDING', 'CONFIRMED', 'CANCELLED', 'EXPIRED'))
);

CREATE TABLE reservation_seats (
  reservation_id  uuid NOT NULL REFERENCES reservations(id) ON DELETE CASCADE,
  seat_id         uuid NOT NULL REFERENCES seats(id),
  showtime_id     uuid NOT NULL REFERENCES showtimes(id),
  price_cents     integer NOT NULL,
  released_at     timestamptz,
  PRIMARY KEY (reservation_id, seat_id)
);

CREATE UNIQUE INDEX reservation_seats_active_uq
  ON reservation_seats (showtime_id, seat_id)
  WHERE released_at IS NULL;
```

### Решения и обоснования

- **`released_at IS NULL` — это и есть определение «место занято».** Отмена и
  истечение проставляют `released_at` на строках мест, и индекс отпускает место.
  Подтверждённая бронь не отпускает никогда — в этом и состоит смысл слова
  «подтверждена». Альтернатива — денормализовать `status` на строки мест — даёт
  ту же работу при переходе (обновить N строк), но дублирует состояние в двух
  местах, где оно может разойтись; `released_at` — одна колонка, у которой нет
  второго источника правды.
- **`showtime_id` продублирован на `reservation_seats`** ровно по одной причине:
  частичный уникальный индекс видит только колонки собственной строки. Это
  единственная денормализация в схеме, и она вынужденная. Совпадение с
  `reservations.showtime_id` не стережёт триггер: обе строки пишет одна
  транзакция из одного значения, другого пути записи не существует. Триггер
  ради инварианта, который нельзя нарушить, — цена без выгоды.
- **`price_cents` фиксируется на момент холда.** Базовая цена сеанса может
  измениться, пока пользователь держит места; должен он ту цену, которую ему
  показали. `total_price_cents` на брони — сумма, посчитанная в той же
  транзакции.
- **`session_id` вместо `user_id`.** Аутентификации нет, и вводить её ради
  внешнего ключа — это технология ради технологии. `users` остаётся засеянной и
  неиспользуемой до под-проекта, где вход в систему решает настоящую задачу.
  Колонка `user_id` заранее не добавляется: `NULL` во всех строках — это не
  задел, а мёртвое поле.
- **`ON DELETE CASCADE` на `reservation_seats`** — строки мест не имеют смысла
  без брони. Удалять брони код не будет (отмена — это статус, а не `DELETE`), но
  каскад делает очистку в тестах и ручные операции безопасными.
- **Индексы:** `reservations (session_id, created_at DESC)` — список броней
  сессии; `reservation_seats (showtime_id) WHERE released_at IS NULL` не нужен,
  его роль исполняет уникальный индекс, который и так частичный по тому же
  предикату и начинается с `showtime_id`.

## 4. Как побеждает ровно один

Одна транзакция, уровень изоляции — дефолтный `READ COMMITTED`, никаких
прикладных локов.

```
1. Прочитать сеанс. Уже начался → 409.
2. Проверить, что все места принадлежат залу этого сеанса → иначе 400.
   Проверить 1 ≤ количество ≤ 10 и отсутствие повторов → иначе 400.
3. Освободить ровно тех блокировщиков, которые стоят на пути:
   PENDING-брони с истёкшим expires_at, держащие запрошенные места.
4. INSERT ... SELECT ... ON CONFLICT DO NOTHING RETURNING seat_id.
5. Вернулось меньше строк, чем запрошено мест → SeatsUnavailableError (409),
   транзакция откатывается.
```

Шаг 3 в SQL:

```sql
WITH blocking AS (
  SELECT DISTINCT r.id
  FROM reservations r
  JOIN reservation_seats rs ON rs.reservation_id = r.id
  WHERE rs.showtime_id = $1
    AND rs.seat_id = ANY($2)
    AND rs.released_at IS NULL
    AND r.status = 'PENDING'
    AND r.expires_at <= now()
),
expired AS (
  UPDATE reservations r SET status = 'EXPIRED', updated_at = now()
  WHERE r.id IN (SELECT id FROM blocking)
  RETURNING r.id
)
UPDATE reservation_seats rs SET released_at = now()
WHERE rs.reservation_id IN (SELECT id FROM expired)
  AND rs.released_at IS NULL;
```

Шаг 4:

```sql
INSERT INTO reservation_seats (reservation_id, seat_id, showtime_id, price_cents)
SELECT $1, s.id, $2, $3 + sc.surcharge_cents
FROM seats s
JOIN seat_categories sc ON sc.code = s.category_code
WHERE s.id = ANY($4)
ON CONFLICT DO NOTHING
RETURNING seat_id;
```

### Решения и обоснования

- **Инвариант в базе, а не в сервисе.** Никакой путь записи — ни будущий
  админский, ни воркер под-проекта 4, ни ошибка в сервисе — не может создать
  двойное бронирование, потому что это запрещено индексом. Проверка
  «свободно ли место» перед вставкой была бы классическим check-then-act:
  две транзакции читают свободное место и обе идут дальше.
- **`ON CONFLICT DO NOTHING` — это и есть механизм ожидания.** Конкурент,
  вставивший строку, но ещё не закоммитивший, заставляет нас **заблокироваться**
  до его коммита или отката, после чего мы либо ничего не делаем (он победил),
  либо вставляем (он откатился). Отдельный лок для этого не нужен: сериализацию
  выполняет сам индекс.
- **`DO NOTHING` без указания арбитра.** Вывод арбитра для частичного индекса
  требует повторения предиката `WHERE released_at IS NULL` в выражении
  `ON CONFLICT`; голая форма ловит конфликт по любому индексу таблицы, а
  уникальный индекс здесь один (плюс первичный ключ, конфликт по которому
  означал бы ошибку в коде и должен падать). Оба варианта корректны, выбран
  короткий.
- **`DO NOTHING ... RETURNING` вместо голого `INSERT` и перехвата `23505`.**
  Оба дают 409. Но `RETURNING` возвращает список мест, которые удалось занять,
  а значит разность даёт список **проигранных** мест — и клиент показывает «C7 и
  C8 только что заняли», а не «что-то пошло не так».
- **Повторы в `seatIds` отклоняются, а не схлопываются.** `seat_id = ANY($4)`
  считает `[A, A]` за одно место, вставит одну строку — и шаг 5 увидит «одна
  строка вместо двух» и соврёт про занятое место. Уникальность проверяет
  Zod-схема, до того как запрос дойдёт до SQL.
- **Всё или ничего.** Запрошено пять мест, одно занято — не занимается ни одно.
  Частичный успех оставил бы пользователя с подмножеством, которое он не
  выбирал, и потребовал бы отдельного UI для «мы дали вам три из пяти».
- **Ленивое истечение ограничено запрошенными местами.** Освобождать все
  просроченные брони сеанса означало бы, что каждая попытка холда на популярном
  сеансе пишет в одни и те же строки — искусственная точка конкуренции ровно
  там, где её меньше всего хотят. Работа шага 3 ограничена размером запроса.
- **Никакого фонового процесса.** Просроченная бронь не мешает никому, потому
  что её снимает тот, кому она мешает. Под-проект 3 заменит ленивую проверку на
  Redis TTL и сообщение об истечении в RabbitMQ — и будет с чем сравнивать.

### Уровень изоляции

`READ COMMITTED`, дефолт. `SERIALIZABLE` здесь ничего не добавляет: инвариант
защищён уникальным индексом, который работает на любом уровне изоляции, а
цена — ошибки сериализации `40001` и цикл повторов на самом горячем пути
проекта. Это фиксируется ADR, потому что «взять SERIALIZABLE и не думать» —
первое, что приходит в голову.

## 5. State machine и владение

```
        ┌──────────► CONFIRMED   (терминальное)
        │
   PENDING ────────► CANCELLED   (терминальное)
        │
        └──────────► EXPIRED     (терминальное)
```

- Переходы проходят через одну чистую функцию `canTransition(from, to)`,
  покрытую unit-тестами. `CHECK`-ограничение в базе стережёт домен значений,
  функция — граф переходов.
- `expires_at = created_at + 10 минут` (раздел 9 `spec.md`). Значение живёт в
  конфиге (`RESERVATION_TTL_SECONDS`), потому что конкурентные тесты должны
  уметь ставить его в секунды.
- **Confirm и cancel берут `SELECT ... FOR UPDATE` на строку брони.** Это
  единственный пессимистический лок в под-проекте, и он нужен: без него
  одновременные confirm и cancel одной брони могут оба прочитать `PENDING` и
  оба записать своё состояние.
- **Confirm перепроверяет `expires_at` под этим локом.** Бронь, истёкшая, пока
  страница чекаута была открыта, подтвердиться не должна → `ReservationExpiredError`.
  Одновременно бронь помечается `EXPIRED`, а места освобождаются: тот, кто
  обнаружил истечение, его и оформляет.
- **Cancel идемпотентен.** Для `CANCELLED` и `EXPIRED` он не выполняет перехода
  (`canTransition` их запрещает — оба состояния терминальны), а возвращает `204`:
  пользователь просил, чтобы места освободились, и они свободны. Ошибка здесь
  сообщала бы о проблеме, которой нет.
- Cancel подтверждённой брони → `InvalidStateTransitionError` (409). Возврат
  денег появится вместе с деньгами.

### Владение

`X-Session-Id` обязателен на всех эндпоинтах броней. Бронь чужой сессии
отвечает **404, а не 403**: 403 подтверждает, что такой идентификатор
существует. Формально это «не найдено среди ваших», что и есть правда с точки
зрения вызывающего.

## 6. Контракт API

```
POST   /api/v1/reservations              { showtimeId, seatIds[] }  → 201
GET    /api/v1/reservations                                          → 200 (список сессии)
GET    /api/v1/reservations/:id                                      → 200
DELETE /api/v1/reservations/:id                                      → 204
POST   /api/v1/reservations/:id/confirm                              → 200
```

Тело брони:

```json
{
  "id": "018f...",
  "showtimeId": "018f...",
  "status": "PENDING",
  "totalPriceCents": 45000,
  "expiresAt": "2026-08-28T12:10:00.000Z",
  "createdAt": "2026-08-28T12:00:00.000Z",
  "seats": [{ "seatId": "018f...", "rowLabel": "C", "seatNumber": 7, "priceCents": 22500 }]
}
```

Места в ответе приходят с геометрией, а не голыми идентификаторами: страница
брони должна показать «ряд C, место 7», не делая второй запрос за картой зала.

`GET /reservations` отдаёт конверт `{ data, nextCursor }` с keyset-пагинацией по
`(created_at DESC, id DESC)` — тот же механизм, что у коллекций под-проекта 1.
Выборка всегда ограничена сессией из заголовка; эндпоинта «все брони» не
существует.

Все пять эндпоинтов регистрируются в генераторе OpenAPI из тех же Zod-схем —
документ на `/api/docs` не может разойтись с валидацией, потому что источник
один.

### Изменения в существующем контракте

`GET /showtimes/:id/seats`:

- `status` считается left join'ом к `reservation_seats` и статусу брони:
  подтверждённая → `CONFIRMED`; `PENDING` и не истёкшая → `HELD`; иначе
  `AVAILABLE`. Предикат истечения тот же ленивый (`expires_at > now()`), так что
  чтение и запись согласованы по определению «занято».
- Добавляется `heldByYou: boolean` — место, которое держит ваша сессия. Без
  этого карта зала не может отличить вашу бронь от чужой и покажет собственные
  места пользователя как недоступные. Эндпоинт остаётся публичным:
  `X-Session-Id` на нём необязателен, без него `heldByYou` всюду `false`.
- `seatStatusSchema` сохраняет три значения; изменение аддитивное.

### Ошибки

Новые наследники `DomainError` (статус и `typeSlug` — на классе, как заведено
под-проектом 1):

| Класс                          | Статус | Когда                                    |
| ------------------------------ | ------ | ---------------------------------------- |
| `MissingSessionError`          | 400    | Нет или невалиден `X-Session-Id`         |
| `SeatsNotInHallError`          | 400    | Место не принадлежит залу сеанса         |
| `InvalidSeatCountError`        | 400    | 0 мест, больше 10 или повтор места       |
| `SeatsUnavailableError`        | 409    | Гонка проиграна; несёт `seatIds`         |
| `ShowtimeAlreadyStartedError`  | 409    | Сеанс уже начался                        |
| `ReservationExpiredError`      | 409    | Confirm истёкшей брони                   |
| `InvalidStateTransitionError`  | 409    | Переход, запрещённый state machine       |

`SeatsUnavailableError` несёт расширение Problem Details:

```json
{
  "type": "https://cinema.example/errors/seats-unavailable",
  "title": "Seats unavailable",
  "status": 409,
  "detail": "Seats C7, C8 were taken by another reservation",
  "instance": "/api/v1/reservations",
  "traceId": "7f8a...",
  "seatIds": ["018f...", "018f..."]
}
```

RFC 9457 расширения разрешает; `problemDetailsSchema` получает необязательное
поле, чтобы клиент мог его прочитать типизированно.

### Лимит в 10 мест

Не бизнес-правило, а граница ресурса: без неё один запрос может попросить все
1000 мест премьерного зала и держать блокировки на них до конца транзакции.
Настоящий rate limiting — раздел 21 `spec.md` и под-проект 7.

## 7. Тесты

Конкурентный тест — не дополнение к под-проекту, а его результат.

| Тест                                            | Что доказывает                                         |
| ----------------------------------------------- | ------------------------------------------------------ |
| N параллельных клиентов, одно место             | Ровно один `201`, N−1 × `409`, одна активная строка     |
| 1000 клиентов, 1000 разных мест премьерного зала | 1000 холдов, ноль конфликтов — индекс не сериализует всё |
| Истёкший холд                                   | Место уходит следующему без единого фонового процесса   |
| Confirm против cancel одной брони               | Побеждает ровно один, второй получает 409               |
| Частичный конфликт (5 мест, одно занято)        | Ноль занятых мест, бронь не создана                     |
| Чужая сессия                                    | 404 на чтение, отмену и подтверждение                   |

### Последствие для харнесса

Под-проект 1 выполняет каждый интеграционный тест в транзакции с откатом.
**Конкурентный тест внутри одной транзакции невозможен** — параллельные клиенты
не увидят друг друга, потому что каждый из них должен коммитить, чтобы стать
видимым остальным.

Харнесс получает второй режим: подготовка данных, выполнение теста настоящими
параллельными соединениями, очистка `TRUNCATE reservations,
reservation_seats CASCADE`. Каталог не трогается — он засеян один раз и только
читается. Существующие тесты остаются на транзакционном режиме: он быстрее и
изолированнее, менять то, что работает, незачем.

Параллелизм создаётся `Promise.all` над настоящими HTTP-запросами к поднятому
приложению, а не вызовами сервиса: тест должен проходить через пул соединений,
пайпы валидации и фильтр ошибок — то есть через то же, через что пойдёт
нагрузка под-проекта 3.

## 8. Фронтенд

### Поток

```
/showtimes/:id           выбор мест → сводка → «Забронировать»
        ↓ POST /reservations
/reservations/:id        таймер, состав брони, «Подтвердить» / «Отменить»
```

### Решения и обоснования

- **Идентификатор сессии** генерируется один раз (`crypto.randomUUID()`),
  живёт в `localStorage`, добавляется заголовком в существующей обёртке
  `shared/api/client.ts`. Одно место, где он появляется, — иначе его забудут
  добавить в новом запросе.
- **Никакого оптимистичного обновления мест.** Оптимистичный холд под
  конкуренцией — это ложь, которую сервер через мгновение опровергнет: место
  подсветилось занятым вами, а через 200 мс вернулось чужим. `409` инвалидирует
  запрос мест и подсвечивает именно те места, которые вы проиграли.
- **Карта зала перезапрашивается каждые 5 секунд** (`refetchInterval`), пока
  страница видима. Под-проект 1 поставил `staleTime` 30 секунд для статичных
  данных; теперь данные меняются под пользователем, и он должен это видеть,
  выбирая места. Подписка вместо поллинга — не сейчас: WebSocket ради экономии
  одного запроса в пять секунд не окупается, а под-проект 5 (Kafka) даст для
  этого настоящий повод.
- **Выбор мест — состояние страницы, не URL и не стор.** URL под-проект 1
  использует для фильтров, потому что ссылка на выборку осмысленна; ссылка на
  «я тыкнул три места, но не забронировал» — нет.
- **Zustand не появляется.** Выбор мест локален для страницы карты, таймер
  локален для страницы брони, серверное состояние держит TanStack Query. Стора
  нечего хранить. Под-проект 1 обещал Zustand здесь — обещание отменяется, а не
  исполняется формально; первый принцип `spec.md` касается и фронтенда.
  То же с React Hook Form: формы нет. Обе библиотеки вернутся к рассмотрению в
  под-проекте 5, где появляется форма оплаты.
- **Таймер** — один хук `useCountdown(expiresAt)`, тикающий раз в секунду.
  По достижении нуля запрос брони инвалидируется, а не переписывается локально:
  истечение объявляет сервер, клиент его только отображает.

### Доступность

- Место — по-прежнему `<button>`; выбор отражается `aria-pressed`, а не только
  цветом или рамкой.
- Занятые места получают `disabled` и `aria-label` с причиной: «ряд C, место 7,
  занято».
- Сводка выбора — `aria-live="polite"`: «выбрано 3 места, 450 ₴».
- Таймер объявляется не каждую секунду, а на пороговых значениях (5 минут,
  1 минута, 30 секунд), иначе скринридер превращается в метроном.

### Состояния экрана

Как в под-проекте 1, проектируются все: скелетон карты, пустая бронь
(не найдена → 404-экран), ошибка холда с перечислением проигранных мест,
истёкшая бронь с предложением выбрать места заново, подтверждённая бронь.

## 10. Что этот под-проект оставляет следующему

- Ленивая проверка истечения — точка, куда под-проект 3 вставит Redis TTL и
  сообщение `reservation.expire` в RabbitMQ.
- Измеримая база: конкурентный тест на 1000 мест даёт цифры, против которых
  сравнивается Redis в эксперименте раздела 25 `spec.md`.
- Переход `PENDING → CONFIRMED` — шов, в который под-проект 5 вставит
  `PAYMENT_PENDING` и платёж, не трогая карту зала и не создавая новых экранов.
- `session_id` — колонка, которая станет `user_id`, когда появится вход.
