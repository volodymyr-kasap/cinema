## 1. Контекст

`spec.md` описывает платформу из 12 фаз: NestJS + PostgreSQL + Redis + RabbitMQ +
Kafka + ClickHouse + Prometheus/Grafana + k6. Одной спекой это не покрывается.
Проект разбит на семь под-проектов, каждый со своей спекой, планом и циклом
реализации:

| # | Под-проект | Фазы `spec.md` | Что появляется |
|---|---|---|---|
| **1** | **Фундамент** | 1 | Монорепо, NestJS + Postgres, схема каталога, read-only API, React SPA до seat map, Docker, CI |
| 2 | Бронирование и конкурентность | 2, 3 | Reservation/Booking, транзакции, state machine, конкурентный тест, UI выбора мест |
| 3 | Redis, expiration, сравнение локов | 4, 5, 20, 25 | Redis-лок, TTL холдов, k6, эксперимент DB vs Redis |
| 4 | Async: RabbitMQ, payment, идемпотентность | 6, 7, 8, 15, 16 | Воркеры, fake payment provider, Idempotency-Key, retry/DLQ, circuit breaker |
| 5 | Kafka и domain events | 9 | Event streaming, consumer groups |
| 6 | Аналитика | 10-14 | Frontend tracking, Analytics API, ClickHouse, batch ingestion, дашборд |
| 7 | Observability и нагрузка | 17-19, 20 | Prometheus/Grafana, correlation ID, rate limiting, финальные прогоны k6 |

Отличия от порядка в `spec.md`: SPA втянут в под-проект 1 (иначе фазы 1-3 нечем
показывать), k6 и rate limiting подтянуты к тем под-проектам, где они реально
нужны — k6 требуется уже для сравнения способов блокировки, иначе сравнивать
нечем.

**Эта спека описывает только под-проект 1.**

### Что есть сейчас

Каталог `cinema-ticket-booking-node/` — рабочее Fastify-приложение на ~600 строк:
статический список фильмов, Redis-лок на `SET NX PX`, Lua-скрипты для
check-then-act, тест на 100 000 конкурентных холдов. Домен там плоский
(фильм → место) и с доменом из `spec.md` (Cinema → Hall → Showtime → Seat) не
совпадает, поэтому кодом оно не переиспользуется. Переносятся идеи: семантика
лока, атомарность через Lua, маппинг доменных ошибок в HTTP-статусы, устройство
конкурентного теста. Прототип остаётся в истории git первым коммитом и удаляется
из рабочего дерева вторым.

### Принятые решения верхнего уровня

| Решение | Выбор |
|---|---|
| Бэкенд-фреймворк | NestJS с нуля, на Fastify-адаптере |
| Доступ к БД | Drizzle |
| Контракт фронт↔бэк | Общий пакет Zod-схем |
| Zustand и React Hook Form | Отложены до под-проекта 2 |
| Репозиторий | `git init` в корне, прототип — в историю |

## 2. Цель и границы

### Цель

Работающий вертикальный срез каталога: пользователь открывает приложение, видит
фильмы, выбирает фильм, кинотеатр и сеанс, попадает на карту зала. Плюс вся
инфраструктурная обвязка, на которую будут опираться под-проекты 2-7.

### В рамках

- Монорепо на npm workspaces: `apps/api`, `apps/web`, `packages/contracts`.
- NestJS-приложение: конфиг, Drizzle, каталог, health-эндпоинты, Problem Details,
  структурированные логи с requestId, graceful shutdown.
- Схема PostgreSQL для каталога и миграции.
- Детерминированный seed, включая зал на 1000 мест.
- React SPA: три маршрута, TanStack Query, Tailwind, доступная seat map.
- Docker Compose на весь стек, Dockerfile для api и web.
- CI: lint, typecheck, unit, интеграционные на Testcontainers, компонентные, e2e smoke.
- ADR на каждое неочевидное решение.

### Вне рамок

Аутентификация и авторизация; любое бронирование, холды и state machine мест;
Redis; RabbitMQ; Kafka; ClickHouse; Prometheus и Grafana; rate limiting; k6;
платежи; Zustand и React Hook Form. Каждое приходит в своём под-проекте вместе с
задачей, которую решает. Главный принцип `spec.md` — «не додаємо технології
заради технологій» — применяется в том числе к фронтенд-библиотекам.

## 3. Структура репозитория

```
cinema/
├── package.json                 # npm workspaces, скрипты верхнего уровня
├── docker-compose.yml
├── .env.example
├── .github/workflows/ci.yml
├── docs/
│   ├── adr/
│   └── superpowers/specs/
├── apps/
│   ├── api/                     # NestJS на Fastify-адаптере
│   └── web/                     # Vite + React
└── packages/
    └── contracts/               # Zod-схемы + выведенные типы
```

**npm workspaces, а не Nx/Turborepo.** Два приложения и один пакет. Nx окупается
на кэшировании графа задач из десятков проектов; здесь он добавит конфигурации
больше, чем сэкономит. Миграция на Turborepo из workspaces дешёвая, если
под-проект 6 разрастётся до отдельного analytics-сервиса и воркеров.

**`packages/contracts`** — единственная зависимость, которую делят фронт и бэк.
Внутри Zod-схемы сущностей и ответов API, сгруппированные по ресурсу
(`movie.ts`, `showtime.ts`, `seat.ts`, `common.ts`), плюс выведенные типы. Ни
Nest-, ни React-специфики внутри быть не должно: пакет обязан собираться
самостоятельно, иначе перестанет быть контрактом и станет свалкой общего кода.

### Модули `apps/api`

| Модуль | Ответственность |
|---|---|
| `ConfigModule` | Парсинг `process.env` через Zod, падение на старте при кривом конфиге |
| `DrizzleModule` | Пул соединений, провайдер `DRIZZLE`, поддержка передачи транзакции |
| `CatalogModule` | Movies, Cinemas, Halls, Showtimes, Seats — чтение |
| `HealthModule` | `/health`, `/ready` |

`CatalogModule` намеренно один, а не четыре модуля по сущности: эти данные
читаются всегда вместе (фильм → сеансы → зал → места), дробить их сейчас — это
границы ради границ. Расщепление произойдёт, когда появится причина.

Отдельного repository-слоя нет: сервисы ходят в Drizzle через инжектируемый
провайдер. Провайдер сразу проектируется так, чтобы принимать транзакцию —
иначе в под-проекте 2 придётся переписывать каждый вызов.

### Структура `apps/web`

```
src/
├── app/          # router, QueryClientProvider, layout, error boundary
├── features/
│   ├── movies/
│   ├── showtimes/
│   └── seat-map/
├── shared/
│   ├── api/      # fetch-обёртка, валидация ответов, фабрика query-ключей
│   └── ui/       # Button, Skeleton, EmptyState, ErrorState, Badge
└── test/         # setup, MSW-хендлеры
```

Feature-папки без догмы feature-sliced design: слои `entities`/`widgets` на этом
объёме — оверинжиниринг.

## 4. Схема данных

Создаётся только каталог плюс `users`. Таблица `users` нужна уже сейчас: на неё
сошлются `reservations` в под-проекте 2, а seed должен создавать
предсказуемых пользователей для интеграционных тестов. Аутентификации в
под-проекте 1 нет — пользователь никак не выбирается и не отображается.

```
users      (id, email, display_name, created_at)
movies     (id, title, description, duration_minutes, poster_url, release_date, rating)
cinemas    (id, name, city, address, timezone)
halls      (id, cinema_id, name)
seats      (id, hall_id, row_label, seat_number, category)
showtimes  (id, movie_id, hall_id, starts_at, ends_at, base_price_cents, language, format)
```

Таблицы `reservations`, `bookings`, `payments`, `tickets` **не создаются**. В
`spec.md` Reservation и Booking — разные сущности, и их разграничение (что такое
hold, что такое оплаченная бронь, где живёт state machine) — центральное решение
под-проекта 2. Зафиксировать его до проектирования флоу означает гарантированную
переделку.

### Решения и обоснования

- **`seats` принадлежат залу, а не сеансу.** Место — физический объект.
  Занятость в под-проекте 2 ляжет на пару `(showtime_id, seat_id)`. Альтернатива
  — копировать места на каждый сеанс — даёт 1000 мест × 100 сеансов = 100 000
  строк-дублей и обесценивает финальный эксперимент раздела 25 `spec.md`.
- **Деньги — `integer` в минорных единицах** (`base_price_cents`), валюта одна на
  всю систему — UAH, отдельным полем не хранится и не конвертируется.
  Мультивалютность не нужна ни одной фазе `spec.md`. Никаких `float`.
- **Время — `timestamptz`, всё хранится в UTC.** Часовой пояс живёт в
  `cinemas.timezone` и применяется только при отображении.
- **Пересечения сеансов запрещает база:**
  `EXCLUDE USING gist (hall_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`,
  требует расширения `btree_gist`. Уникальный индекс по `(hall_id, starts_at)`
  этого не ловит: сеанс может начаться в середине предыдущего.
- **ID — UUID v7.** Публичные идентификаторы не должны раскрывать объёмы
  бизнеса; v7 монотонен по времени и, в отличие от v4, не разрушает локальность
  B-tree при вставке. `bigserial` был бы компактнее в индексах — осознанный
  размен на непредсказуемость ID.
- **Уникальность места в зале:** `UNIQUE (hall_id, row_label, seat_number)`.
- **Никаких денормализованных счётчиков** (`rows_count` и подобных): вычисляются
  из `seats`, рассинхронизировать нечего.
- **Индексы:** `showtimes (movie_id, starts_at)`, `showtimes (hall_id, starts_at)`,
  `seats (hall_id)`, `halls (cinema_id)`.

### Миграции

`drizzle-kit generate`, SQL-файлы коммитятся в репозиторий. Не `push`: на
проекте про транзакции нужно уметь показать сам DDL и его откат. Применяются
командой `npm run db:migrate` отдельным шагом, не в бутстрапе приложения.

### Seed

Детерминированный (фиксированный seed генератора), чтобы тесты и скриншоты
воспроизводились: ~10 фильмов, 3 кинотеатра, 12 залов, сеансы на 14 дней вперёд.
Среди залов один «премьерный» на **1000 мест** — тот самый из раздела 25
`spec.md`, чтобы эксперимент под-проекта 3 не требовал новых данных. Места
разных категорий (`STANDARD`, `VIP`, `RECLINER`) с разной надбавкой к цене: это
даёт seat map визуальную содержательность в под-проекте 1, где занятых мест ещё
нет, и понадобится для revenue-метрик фазы 14.

## 5. Контракт API

### Эндпоинты

```
GET /api/v1/movies?cursor=&limit=
GET /api/v1/movies/:id
GET /api/v1/cinemas
GET /api/v1/cinemas/:id
GET /api/v1/showtimes?movieId=&cinemaId=&date=&cursor=&limit=
GET /api/v1/showtimes/:id
GET /api/v1/showtimes/:id/seats
GET /health
GET /ready
```

Версия в пути с первого дня (Nest URI versioning): добавить её потом, когда
фронт уже ходит на голые пути, — ломающее изменение, а под-проекты 4-6 контракт
точно тронут.

### Форма ответов

Коллекции — конверт `{ data: [...], nextCursor: string | null }`, одиночные
ресурсы — голый объект. Пагинация **keyset**, не offset: offset деградирует на
больших смещениях и пропускает либо дублирует записи при вставках между
запросами, а сеансы вставляются постоянно.

Поля — **camelCase**: единый стиль с TypeScript по обе стороны. Прототип
использовал snake_case; раз API пишется заново, тащить это незачем.

`/showtimes/:id/seats` возвращает места зала с геометрией (`rowLabel`,
`seatNumber`), категорией, посчитанной ценой (`базовая цена сеанса + надбавка
категории`; считает бэкенд — фронт не должен знать формулу ценообразования) и
полем `status`. В под-проекте 1 `status` всегда `AVAILABLE`, поскольку
бронирований не существует. Поле вводится сразу: это шов, в который в
под-проекте 2 войдут `HELD` и `CONFIRMED`, и seat map не придётся переписывать.

### Ошибки

RFC 9457 Problem Details, `Content-Type: application/problem+json`:

```json
{
  "type": "https://cinema.example/errors/showtime-not-found",
  "title": "Showtime not found",
  "status": 404,
  "detail": "Showtime 018f... does not exist",
  "instance": "/api/v1/showtimes/018f...",
  "traceId": "7f8a..."
}
```

Стандарт вместо самодельного `{ "error": "..." }`. `traceId` в теле — задел под
фазу 19: по нему находится весь lifecycle запроса. Реализация — один глобальный
exception filter; доменные ошибки наследуют базовый `DomainException`, HTTP-статус
живёт в классе ошибки, а не в контроллере.

### Валидация

Zod-схемы из `packages/contracts` применяются единым `ZodValidationPipe` к query
и params. Ответы валидируются теми же схемами **только в dev и тестах**: это
ловит расхождение «схема сказала одно, репозиторий вернул другое» в момент
появления, но не тратит CPU в проде.

### OpenAPI

Генерируется из тех же Zod-схем (`zod-to-openapi`) и отдаётся на `/api/docs`.
Документация не может разойтись с валидацией, потому что источник один.

### Клиентская сторона контракта

Обёртка в `shared/api` валидирует ответ схемой из `contracts` и разворачивает
Problem Details в типизированную ошибку, которую TanStack Query кладёт в `error`.
Цена — парсинг на каждом ответе; выгода — рассогласование контракта видно как
явная ошибка, а не как `undefined` в глубине рендера.

## 6. Фронтенд

### Маршруты

```
/                        список фильмов
/movies/:movieId         фильм и его сеансы (фильтры: город, дата)
/showtimes/:showtimeId   карта зала
```

React Router в декларативном режиме, **без loaders**: data router даёт второй
механизм загрузки данных параллельно TanStack Query, а два кэша — это два места,
где что-то может протухнуть. Загрузка целиком в Query, роутер отвечает только за
URL.

**Фильтры живут в query-параметрах**, а не в React-стейте: ссылка на конкретную
выборку шарится, кнопки «назад» и «вперёд» работают. Это же — содержательная
причина отсутствия Zustand в под-проекте 1: сервер-стейт держит Query, UI-стейт
держит URL, отдельному стору нечего хранить.

### TanStack Query

- Типизированная фабрика ключей в `shared/api/query-keys.ts`, не строки по месту
  вызова: иначе точечная инвалидация в под-проекте 2 начнёт промахиваться.
- `staleTime`: каталог — 5 минут, места — 30 секунд (в под-проекте 2 станет
  коротким поллингом или подпиской).
- Пагинация через `useInfiniteQuery` с `placeholderData`, чтобы список не
  схлопывался при подгрузке.
- Префетч сеансов при наведении на карточку фильма.

### Seat map

Главный визуальный компонент и он же нагрузочный: премьерный зал из seed — 1000
мест.

- CSS Grid, на место — `<button>`, а не SVG: клавиатура и скринридер работают без
  дополнительной работы.
- Компонент места мемоизирован, подписка на состояние — по конкретному `seatId`.
  В под-проекте 1 состояние статично, но структура закладывается сразу: в
  под-проекте 2 клик по месту должен перерисовывать одно место, а не зал из
  тысячи узлов.
- Статус и категория различаются **не только цветом** (паттерн или иконка):
  иначе интерфейс, где цвет несёт всю информацию, нечитаем при дальтонизме.
- Roving tabindex по сетке: стрелки ходят вдоль ряда и между рядами, `aria-label`
  вида «Ряд D, место 12, VIP, 320 ₴, свободно».

### Стили

Tailwind v4, токены в CSS-переменных, тёмная тема через `prefers-color-scheme` и
переключатель. Библиотека компонентов не подключается: нужно пять примитивов
(`Button`, `Skeleton`, `EmptyState`, `ErrorState`, `Badge`). Radix появится в
под-проекте 2, если понадобится доступный диалог чекаута.

### Состояния экрана

Проектируются все четыре, не только счастливый путь:

- **skeleton** — не спиннер: скелетон сохраняет layout и не даёт скачка контента;
- **empty** — «на эту дату сеансов нет» плюс действие сброса фильтра;
- **error** — текст из Problem Details плюс retry;
- **error boundary на маршрут** — падение seat map не должно уносить приложение.

### Тесты фронтенда

Vitest + Testing Library + MSW.

- Компонентные тесты фич против MSW-хендлеров, чьи фикстуры генерируются из
  Zod-схем `contracts`: мок не может разойтись с контрактом.
- Unit: форматирование цен и дат, построение сетки зала из плоского списка мест,
  логика roving tabindex.
- Снапшотов нет: они фиксируют разметку, а не поведение, и гниют.

## 7. Инфраструктура, тесты бэкенда, CI

### Docker Compose

Сервисы: `postgres` (healthcheck `pg_isready`), одноразовый `migrate` (ждёт
healthy, применяет миграции, завершается), `api`, `web`.

Миграции — отдельный сервис, а не шаг в бутстрапе Nest: при нескольких репликах
в под-проектах 6-7 параллельный бутстрап начнёт выполнять DDL наперегонки.

`api` — multi-stage Dockerfile, non-root пользователь, в рантайме только
прод-зависимости. Шероховатость npm workspaces: в билд-стейдж копируются
корневые `package.json` и `package-lock.json` вместе с манифестами воркспейсов
до `npm ci`, иначе ломается кэш слоёв. `web` собирается в статику и отдаётся
nginx — так же, как поедет в прод.

### Конфигурация

`.env.example` в репозитории, парсинг через Zod при старте, падение сразу и с
внятным сообщением. Приложение с кривым `DATABASE_URL` не должно подниматься и
отвечать 500 на каждый запрос.

### Логи и корреляция

pino (на нём и так работает Fastify-адаптер), JSON в проде, pretty в dev.
`requestId` генерируется на входе, живёт в `AsyncLocalStorage`, попадает в каждую
строку лога и в `traceId` тела ошибки. Это часть фазы 19, сделанная заранее за
десяток строк: прикручивать корреляцию задним числом дороже.

### Graceful shutdown

`enableShutdownHooks`: на SIGTERM приложение перестаёт принимать соединения,
дожидается текущих, закрывает пул. Иначе rolling-restart в нагрузочных сценариях
под-проекта 7 будет давать ложные ошибки.

### Тесты бэкенда

Jest (дефолт NestJS, как в `spec.md`).

- Unit — сервисы с подменёнными зависимостями.
- **Интеграционные — против реального PostgreSQL через Testcontainers.**
  Миграции применяются в setup, каждый тест выполняется в транзакции с откатом.
  Ни sqlite, ни моков репозиториев: проект посвящён транзакциям, exclusion
  constraints и уровням изоляции, а всё это существует только в настоящем
  Postgres — мок тестировал бы мок.

### E2E

Один Playwright smoke «каталог → фильм → сеанс → seat map» на поднятом
docker-compose. Это единственный тест, проверяющий, что весь стек стартует и
склеен, — на проекте, который будут клонировать и запускать, это окупается.

### CI (GitHub Actions)

Джобы: `lint + typecheck` → `test:api` (Testcontainers) ∥ `test:web` (Vitest) →
`build` (обе Docker-сборки) → `e2e` (compose + Playwright). Кэш npm по
`package-lock.json`.

### Линтинг

ESLint 9 flat config + Prettier, pre-commit через lint-staged. Biome был бы
быстрее и одним инструментом, но ESLint — то, что ожидают в Nest-проекте, и у
него есть нужные плагины (`@typescript-eslint`, `eslint-plugin-drizzle`, который
ловит `UPDATE`/`DELETE` без `where`).

## 8. ADR

DoD `spec.md` требует уметь обосновать каждое архитектурное решение. Значит
решения записываются в момент принятия: `docs/adr/NNN-*.md`, по 15-20 строк —
контекст, решение, отвергнутые альтернативы, последствия.

Ожидаемый набор в под-проекте 1:

1. NestJS с нуля вместо развития Fastify-прототипа
2. Drizzle как слой доступа к данным
3. Общий пакет Zod-схем вместо кодогенерации из OpenAPI
4. UUID v7 в качестве первичных ключей
5. Keyset-пагинация вместо offset
6. Exclusion constraint для пересечения сеансов
7. Testcontainers вместо моков репозиториев
8. Отсутствие Redis на этом этапе (ради чистоты сравнения в под-проекте 3)

## 9. Definition of Done

1. `git clone && docker compose up` даёт работающий стек с seed-данными.
2. Кликабельный путь: каталог → фильм → сеанс → карта зала на 1000 мест.
3. `/api/docs` отдаёт OpenAPI, сгенерированный из тех же схем, что валидируют
   запросы.
4. CI зелёный: lint, typecheck, unit, интеграционные на Testcontainers,
   компонентные, e2e smoke.
5. README объясняет запуск и отсылает к ADR за обоснованиями.
