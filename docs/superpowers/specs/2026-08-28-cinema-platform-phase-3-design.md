## 1. Контекст

Под-проект 2 закончен: место нельзя занять дважды, и это доказано тестом —
пятьдесят одновременных клиентов дают ровно один `201` и сорок девять `409`.
Инвариант живёт в частичном уникальном индексе, не в сервисе.

Под-проект 3 закрывает разделы 8 и 25 `spec.md`. Redis входит в систему не
потому, что он есть в списке технологий, а потому, что у базового решения есть
измеримая цена: **каждый проигравший платит транзакцией**. Девять тысяч
проигравших занимают девять тысяч соединений из пула, открывают транзакцию и
блокируются внутри `ON CONFLICT` до коммита победителя. Конкуренция за место
превращается в очередь за соединением. Redis должен отсекать проигравших на
входе — за один round-trip, не доходя до Postgres.

Утверждение «должен» здесь недостаточно. ADR 0008 отложил Redis именно ради
того, чтобы у сравнения была честная база; под-проект 3 обязан сравнение
провести и записать цифры.

### Швы, оставленные под-проектом 2

| Шов                                                         | Что с ним делает под-проект 3                                  |
| ----------------------------------------------------------- | -------------------------------------------------------------- |
| Ленивое истечение холдов (ADR 0011)                         | Остаётся авторитетным. Redis добавляет TTL ключа, не заменяет  |
| Конкурентный тест на 1 и на 1000 мест                       | Становится базой сравнения и повторяется для Redis-стратегии    |
| `DATABASE_POOL_MAX` как настраиваемый параметр              | Становится осью нагрузочного эксперимента                       |
| Зал на 1000 мест в seed                                     | Становится сценой эксперимента раздела 25                       |
| Один экземпляр API в Compose                                | Превращается в N реплик за балансировщиком                      |
| `PENDING → CONFIRMED` как шов для платежа                   | Не трогаем: это под-проект 5                                    |

### Принятые решения верхнего уровня

| Вопрос                             | Решение                                                             |
| ---------------------------------- | ------------------------------------------------------------------- |
| Роль Redis                         | Совещательная блокировка перед транзакцией; инвариант остаётся в БД  |
| Выбор стратегии                    | `LOCK_STRATEGY=db\|redis`, обе стратегии живут в коде одновременно   |
| Время жизни ключа                  | Длина холда: `SET ... NX EX 600`, снятие — Lua compare-and-delete    |
| Redis недоступен                   | Fail open: запрос идёт по пути под-проекта 2                         |
| Топология                          | N реплик API за nginx, Redis в стеке                                 |
| Измерение                          | k6: прогон корректности (10 000 попыток) + прогон производительности |
| Фронтенд                           | Не меняется                                                          |

## 2. Цель и границы

### Цель

Показать цифрами, чего стоит блокировка в базе и что даёт блокировка в Redis,
не потеряв ни одной гарантии корректности, доказанной под-проектом 2.

Формулировка результата — из раздела 25 `spec.md`:

```
10 000 попыток
        ↓
1 000 успешных броней
        ↓
0 двойных бронирований
```

для **обеих** стратегий, плюс таблица throughput / p95 / p99 / error rate,
по которой видно, где у каждой стратегии колено.

### В рамках

- Порт `SeatLock` и два адаптера: `NoopSeatLock` (стратегия `db`) и
  `RedisSeatLock`.
- Подключение к Redis: провайдер, healthcheck контейнера, закрытие на shutdown.
- Ключи мест, TTL, снятие блокировки со сверкой владельца (Lua).
- Поведение при отказе Redis и при расхождении Redis и Postgres.
- Генерация идентификатора брони в приложении (значение блокировки нужно до
  вставки строки).
- Кеш геометрии мест в процессе — чтобы 409 на быстром пути нёс метки мест, не
  ходя в базу.
- Топология Compose: N реплик API за nginx, корректное разрешение DNS.
- Нагрузочные сценарии k6 и отчёт с результатами.
- Интеграционные тесты обеих стратегий, включая истечение, владение, отказ
  Redis и оба направления расхождения.
- ADR на каждое неочевидное решение.

### Вне рамок

RabbitMQ и сообщение `reservation.expire`, `Idempotency-Key`, circuit breaker,
rate limiting, Prometheus и Grafana, Redis как кеш карты зала, платежи,
аутентификация, таблицы `bookings` / `payments` / `tickets`.

Отдельно про четыре вещи, которых здесь ждут и которых не будет:

- **`Idempotency-Key` — не здесь.** Раздел 8 `spec.md` называет идемпотентность
  среди того, что исследуется вместе с Redis, но идемпотентность имеет смысл
  там, где повтор стоит денег: раздел 12 и под-проект 5. То, что появляется
  сейчас, — идемпотентность *снятия* блокировки: повторный `release` чужой
  брони не делает ничего, и это проверяется тестом.
- **Circuit breaker — не здесь.** Правильный следующий шаг после fail open, но
  раздел 20 и под-проект 5 дадут ему настоящего клиента (платёжный провайдер) и
  общую абстракцию. Написать его сейчас — написать дважды.
- **Redis не становится кешем карты зала.** Занятость по-прежнему читается из
  Postgres: одно определение «занято», как договорились в ADR 0011. Кеш чтения —
  другая задача с другой ценой (инвалидация), и она не решает проблему этого
  под-проекта.
- **Метрики Prometheus — не здесь.** Счётчики отказов Redis существуют, но живут
  в логах и в выводе k6. Раздел 22 придёт со своим под-проектом и заберёт их
  целиком.

## 3. Архитектура блокировки

### Порт и адаптеры

`apps/api/src/locking/`:

| Файл                  | Содержимое                                                             |
| --------------------- | ---------------------------------------------------------------------- |
| `seat-lock.ts`        | Интерфейс `SeatLock`, токен `SEAT_LOCK`, формат ключа в одном месте     |
| `noop-seat-lock.ts`   | Стратегия `db`: все методы возвращают «успех» и ничего не делают        |
| `redis-seat-lock.ts`  | `SET NX EX` пайплайном, Lua-снятие, обработка отказов                   |
| `redis.module.ts`     | Провайдер соединения и `onApplicationShutdown`, зеркало `DrizzleModule` |
| `locking.module.ts`   | Фабрика: читает `LOCK_STRATEGY` и связывает `SEAT_LOCK` с адаптером     |

```ts
export interface SeatLock {
  /** Забрать места. Возвращает список тех, которые забрать не удалось. */
  acquire(showtimeId: string, seatIds: string[], reservationId: string): Promise<string[]>;
  /** Снять свои блокировки. Чужие не трогает. Идемпотентно. */
  release(showtimeId: string, seatIds: string[], reservationId: string): Promise<void>;
  /** Продлить до конца жизни занятости места (подтверждённая бронь). */
  retain(showtimeId: string, seatIds: string[], reservationId: string, until: Date): Promise<void>;
}
```

Три метода — весь контракт. `NoopSeatLock.acquire` возвращает пустой массив
(ничего не проиграно), остальное — `void`. Это важнее, чем кажется: стратегия
`db` — не «другая ветка кода», а тот же самый код с адаптером, который ничего
не делает. Значит, сравнение измеряет блокировку, а не две разные реализации.

### Поток создания брони

```
create(sessionId, input)
  │
  ├─ 0. reservationId = uuidv7()                     ← в приложении, не в БД
  │
  ├─ 1. lost = seatLock.acquire(showtimeId, seatIds, reservationId)
  │        lost непуст → снять свои → 409 SeatsUnavailable
  │        транзакция не открывается, соединение из пула не берётся
  │
  ├─ 2. db.transaction(...)                          ← под-проект 2, без изменений
  │        сеанс → места зала → ленивое истечение → INSERT ... ON CONFLICT
  │        частичный уникальный индекс по-прежнему инвариант
  │
  └─ 3. транзакция бросила → seatLock.release(...)
         успех → вернуть бронь
```

`confirm` вызывает `retain` (ключ переставляется на время до начала сеанса),
`cancel` и ленивое истечение вызывают `release`. Все три — после коммита
транзакции: снимать блокировку внутри транзакции, которая может откатиться, —
значит освободить место, которое всё ещё занято.

### Решения и обоснования

- **Блокировка совещательная, инвариант — в базе.** Отсутствие ключа никогда не
  означает «место точно свободно», оно означает «Redis об этом не знает».
  Именно поэтому холодный, сброшенный или упавший Redis деградирует ровно в
  поведение под-проекта 2, а не в двойное бронирование. Обратный дизайн — Redis
  как источник истины (ADR 0009 наоборот) — требует, чтобы `FLUSHALL` не мог
  случиться никогда, а он может.
- **Стратегия выбирается конфигом, старый путь не удаляется.** Сравнение,
  которое нельзя перезапустить, — не результат, а анекдот. Пока обе стратегии
  живут в коде, эксперимент воспроизводим на любом коммите; если бы `db`-путь
  был удалён, базой служил бы старый тег, собранный другим компилятором с
  другими зависимостями.
- **Один вызов до транзакции, один после.** Соблазн — «умный» адаптер, который
  сам открывает транзакцию и знает про Drizzle. Тогда порт перестаёт быть
  портом, а `create()` — единственным местом, где написан порядок действий.
- **Идентификатор брони генерируется приложением.** Значение блокировки должно
  быть известно **до** того, как строка вставлена, иначе снять блокировку по
  владельцу невозможно. `uuidv7()` в приложении вместо дефолта `uuidv7()` в
  Postgres — ADR 0004 (упорядоченные во времени ключи) не нарушается, дефолт в
  схеме остаётся как страховка для любого другого пути записи.
  Альтернатива — значение `sessionId` — ломается на честном сценарии: одна
  сессия отменяет старую бронь и удаляет ключ, который уже принадлежит её же
  новой броне на то же место.
- **`retain`, а не `release`, при подтверждении.** Подтверждённое место не
  освобождается никогда. Удалить ключ — значит разрешить следующему запросу
  взять блокировку, дойти до транзакции и получить 409 от индекса: корректно,
  но ровно та работа, ради устранения которой Redis и появился. TTL до начала
  сеанса: после начала холды всё равно запрещены (`ShowtimeAlreadyStartedError`),
  поэтому ключу незачем переживать сеанс.

## 4. Ключи, TTL и снятие

Формат ключа — из раздела 8 `spec.md`, дословно:

```
seat:{showtimeId}:{seatId}   →   {reservationId}
```

Захват — пайплайн из N команд (N ≤ 10, ограничение контракта):

```
SET seat:{showtimeId}:{seatId} {reservationId} NX EX {RESERVATION_TTL_SECONDS}
```

Снятие — Lua, потому что «прочитать значение, сравнить, удалить» тремя командами
это тот же check-then-act, от которого ушли в базе: между `GET` и `DEL` ключ
может истечь и быть перезахвачен другим, и тогда мы удалим чужую блокировку.

```lua
-- KEYS: ключи мест, ARGV[1]: идентификатор брони
local removed = 0
for i = 1, #KEYS do
  if redis.call('GET', KEYS[i]) == ARGV[1] then
    removed = removed + redis.call('DEL', KEYS[i])
  end
end
return removed
```

`retain` — такой же скрипт с `SET KEYS[i] ARGV[1] EX ARGV[2]` вместо `DEL`, и
той же сверкой владельца.

### Решения и обоснования

- **Частичный захват откатывается.** Если из трёх мест взялись два, оба
  немедленно снимаются, и клиент получает 409 со списком проигранных. Оставить
  «свои» два висеть на десять минут — заблокировать места, которые никто не
  держит, ради запроса, который уже провалился.
- **Ключи не берутся в отсортированном порядке.** В базе порядок обязателен:
  `INSERT` **ждёт** конкурента и без общего порядка две транзакции встают в
  deadlock (ADR 0010). `SET NX` не ждёт — он немедленно возвращает провал, —
  поэтому цикла ожидания не существует и сортировать нечего.
- **TTL ключа и `expires_at` строки считаются от разных часов.** Строка — от
  `now()` Postgres (ADR 0011), ключ — от часов Redis, и они могут разойтись на
  доли секунды. Для авторитетного значения это была бы ошибка; для совещательной
  блокировки — нет: ключ, истёкший чуть раньше строки, пропускает запрос к
  транзакции, где занятость проверяется настоящим предикатом.
- **Пайплайн, а не `MSET`/транзакция Redis.** Нужен ответ по каждому ключу
  отдельно — какие взялись, какие нет; `MULTI` даёт атомарность, которая здесь
  не требуется (частичный захват мы всё равно откатываем сами) и стоит
  блокировки сервера.

## 5. Отказы и расхождения

### Redis недоступен

Ошибка соединения или таймаут команды (`REDIS_COMMAND_TIMEOUT_MS`, по умолчанию
200 мс) логируется на уровне `warn` со счётчиком и **не прерывает запрос**:
`acquire` возвращает пустой список проигравших, и запрос идёт в транзакцию.

- Корректность никогда не зависела от Redis, поэтому деградация теряет
  пропускную способность, а не гарантии.
- `/ready` **не проверяет Redis**. Проверять — значит вывести все реплики из
  ротации из-за подсистемы, без которой система работает. Готовность по-прежнему
  означает «Postgres отвечает».
- Отказ на `release` опаснее отказа на `acquire`: ключ останется висеть до TTL и
  будет держать место, которое уже свободно в базе. Это ограниченный по времени
  ложный отказ, он самоизлечивается, и он же — причина, по которой TTL ключа
  равен длине холда, а не суткам.

### Две стороны расхождения

| Ситуация                             | Что происходит                             | Оценка                                       |
| ------------------------------------ | ------------------------------------------ | -------------------------------------------- |
| Ключ есть, активной строки нет       | 409, места на самом деле свободны          | Ложный отказ, живёт не дольше TTL, допустим  |
| Ключа нет, активная строка есть      | Проходим к транзакции, 409 от индекса      | Инвариант отработал, лишняя транзакция       |

Обе ситуации проверяются тестами. Первая — цена совещательной блокировки, и цена
осознанная: пользователь видит «место занято» на месте, которое освободилось
секунду назад. Вторая — доказательство, что индекс остаётся последним словом.

### Метки мест на быстром пути

`SeatsUnavailableError` несёт метки («C7», «C8») — их видит пользователь. На
быстром пути мест в базе ещё не читали. Ходить за метками в Postgres для каждого
проигравшего — вернуть в систему ровно ту нагрузку, ради устранения которой всё
это делается: девять тысяч чтений вместо девяти тысяч транзакций.

Решение: геометрия мест зала кешируется в процессе (`seatId → rowLabel,
seatNumber`), лениво, по залу, при первом обращении. Данные каталога засеяны
один раз и в этом под-проекте неизменяемы, поэтому инвалидации не существует —
и это записано как ограничение: когда появится админка, редактирующая места,
кеш получит шов для сброса. Альтернатива — сделать `label` необязательным в
контракте — портит ответ ради внутренней детали реализации.

## 6. Топология

```
        k6 ──► nginx :8080 ──┬──► api #1 ──┐
                             ├──► api #2 ──┼──► postgres
                             └──► api #3 ──┘
                                    │
                                    └──────► redis
```

- `api` получает `deploy: replicas: ${API_REPLICAS:-3}` и **теряет
  опубликованный порт**: Compose не публикует фиксированный порт на
  масштабируемом сервисе. Прямой доступ к API (Swagger UI, curl) переезжает на
  `http://localhost:8080/api/`. Файл `docker-compose.single-api.yml` возвращает
  прежнюю форму с одним экземпляром на порту 3000 для повседневной разработки.
- `redis:8-alpine` добавляется в стек с healthcheck (`redis-cli ping`); `api`
  ждёт его готовности.
- `apps/web/nginx.conf` — тот же nginx, что раздаёт SPA, становится
  балансировщиком — получает `resolver 127.0.0.11 valid=10s;` и `proxy_pass`
  через переменную.

Последнее — не косметика. Без переменной nginx резолвит `api` **один раз при
старте** и до перезагрузки шлёт весь трафик в одну реплику. Стек выглядит
сбалансированным, эксперимент измеряет один контейнер, и цифры получаются
красивые и бессмысленные. Это самый вероятный способ получить фальшивый
результат в этом под-проекте, поэтому:

- в `apps/web/nginx.conf` стоит комментарий с объяснением;
- API отдаёт заголовок `X-Instance-Id` (hostname контейнера), k6 считает ответы
  по репликам, и прогон падает, если хотя бы одна реплика обслужила меньше
  половины равной доли (при трёх репликах — меньше 16,7 % запросов).

## 7. Конфигурация

| Переменная                  | По умолчанию             | Назначение                                        |
| --------------------------- | ------------------------ | ------------------------------------------------- |
| `LOCK_STRATEGY`             | `db`                     | `db` \| `redis`                                   |
| `REDIS_URL`                 | `redis://localhost:6379` | Обязательна, если стратегия `redis`               |
| `REDIS_COMMAND_TIMEOUT_MS`  | `200`                    | Порог, после которого срабатывает fail open       |
| `API_REPLICAS`              | `3`                      | Только для Compose                                |

`db` по умолчанию — намеренно: новая подсистема не включается сама собой,
включение — явное действие. Валидация в `env.ts`: при `LOCK_STRATEGY=redis`
без `REDIS_URL` процесс не стартует, а не отвечает 500 на каждый запрос.

Клиент — `ioredis`: пайплайны, `defineCommand` для Lua-скриптов с кешированием
по SHA и предсказуемое поведение таймаутов.

## 8. Тесты

Global setup поднимает контейнер Redis рядом с Postgres (`testcontainers`,
`redis:8-alpine`), URL пишется в файл так же, как `DATABASE_URL`.

Конкурентная сюита под-проекта 2 **параметризуется по стратегиям**: гарантии не
предполагаются для нового пути, а доказываются заново.

| Сценарий                                       | Ожидание                                                         |
| ---------------------------------------------- | ---------------------------------------------------------------- |
| 50 клиентов, одно место, обе стратегии         | Ровно один `201`, сорок девять `409`, ни одного другого статуса   |
| 1000 разных мест одновременно, обе стратегии   | 1000 успехов: сериализуется место, а не сеанс                     |
| Истечение блокировки (`TTL=1s`)                | Ключа нет, место снова берётся                                    |
| Владение                                       | `release` от чужой брони не удаляет ключ                          |
| Повторный `release`                            | Ничего не делает, ошибки нет                                      |
| Подтверждение                                  | Ключ жив после `confirm`, TTL ≈ до начала сеанса                  |
| Отмена и ленивое истечение                     | Ключ удалён                                                       |
| Redis недоступен                               | Холд успешен по пути БД, залогирован `warn`, счётчик увеличен     |
| Ключ есть, строки нет                          | `409` — задокументированный ложный отказ                          |
| Ключа нет, строка есть                         | `409` от индекса — инвариант как последнее слово                  |
| Частичный захват (2 из 3)                      | `409`, оба взятых ключа сняты                                     |

Юнит-тесты: формат ключа, разбор `LOCK_STRATEGY` в `env.ts`, кеш геометрии мест.

CI прогоняет всё это (testcontainers нужен только демон Docker на раннере).
Прогоны k6 в CI не идут: двухминутный нагрузочный тест — не то, что стоит между
разработчиком и мержем. Команда запуска задокументирована в README.

## 9. Эксперимент

Каталог `load/` в корне, запуск через профиль Compose `load` (образ
`grafana/k6` в сети стека — генератор нагрузки не конкурирует с SPA за loopback
хоста и ходит прямо в nginx).

### Прогон 1 — корректность

10 000 попыток занять места зала-«премьеры» на 1000 мест, по одному месту на
запрос.

Выбор места **детерминированный**: попытка *n* берёт место `n mod 1000`, то есть
за каждое место борются ровно десять клиентов. Случайный выбор оставил бы в
среднем 0,05 незанятого места (задача о собирателе купонов при 10 000 бросках на
1000 корзин) — тест, падающий раз в двадцать прогонов по причине, не имеющей
отношения к блокировкам.

Проверяется:

```
ровно 1 000 × 201
ровно 9 000 × 409
ноль 5xx
SQL: активных строк reservation_seats = 1000, дублей (showtime_id, seat_id) нет
```

Это pass/fail, не зависящий от того, насколько быстра машина.

### Прогон 2 — производительность

`ramping-arrival-rate`: 100 → 500 → 1000 → 2000 RPS (раздел 24 `spec.md`).
Модель «частота прибытия», а не «число VU»: при фиксированном числе VU
замедляющаяся система сама себе снижает нагрузку и выглядит здоровой, а при
фиксированной частоте перегрузка честно проявляется ростом очереди.

Снимается: throughput, p95, p99, error rate, доля 409, распределение по репликам
и точка колена.

### Условия и отчёт

Обе стратегии стартуют с одинакового состояния: `npm run load:reset` — `TRUNCATE
reservations, reservation_seats CASCADE` плюс `FLUSHALL`. Результаты — в
`docs/experiments/2026-08-28-db-vs-redis-locking.md`: железо, версии образов,
число реплик, `DATABASE_POOL_MAX`, таблица цифр, выводы.

### Предсказание, записанное до прогона

`db`-путь должен деградировать раньше: каждый из девяти тысяч проигравших
занимает соединение из пула и блокируется внутри `ON CONFLICT` до коммита
победителя, то есть конкуренция за место превращается в очередь за соединением,
и колено ожидается вблизи `DATABASE_POOL_MAX × число реплик`. `redis`-путь
должен отбивать проигравших за один round-trip, не открывая транзакции, и
упираться в другое — в сеть и в однопоточность Redis.

Если цифры скажут иначе, в отчёте будет написано именно это. Эксперимент,
способный только подтвердить свою гипотезу, — не эксперимент; и в этом случае
вывод «Redis здесь не нужен» будет таким же законным результатом под-проекта,
как и обратный.

## 11. Что этот под-проект оставляет следующему

- **Ленивое истечение всё ещё авторитетно.** ADR 0011 предполагал, что
  под-проект 3 заменит его TTL Redis. Замены не происходит и не может: истечение
  ключа не пишет в Postgres, а источник истины — Postgres. Настоящую замену
  делает `reservation.expire` в RabbitMQ — под-проект 4.
- **Счётчики отказов Redis, попаданий блокировки и распределения по репликам**
  существуют в логах и ждут раздела 22: у Prometheus будет что собирать в первый
  же день.
- **Fail open — место для circuit breaker** (раздел 20, под-проект 5): сейчас
  каждый запрос при мёртвом Redis платит таймаутом.
- **Топология с несколькими репликами** — предпосылка для всего, что дальше:
  воркеры, консьюмеры и идемпотентность имеют смысл только там, где экземпляров
  больше одного.
- **Цифры эксперимента** становятся базой, против которой сравнивается всё
  последующее: очередь RabbitMQ, батчинг ClickHouse и оптимизация раздела 12.
