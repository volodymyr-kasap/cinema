# Cinema Booking Platform — под-проект 5: платёж, идемпотентность и circuit breaker

**Дата:** 2026-09-03
**Статус:** утверждён
**Источник требований:** `spec.md` (разделы 11, 12, 20; фаза 5 раздела 27)
**Предыдущая спека:** `2026-09-01-cinema-platform-phase-4-design.md`

---

## 1. Контекст

Под-проект 4 закончен: `reservation.expire` ходит через `cinema.commands`,
воркер живёт второй точкой входа того же образа, лестница ретраев и DLQ
проверены тестами с внедрением отказов, а ленивое истечение осталось
авторитетным (ADR 0030). Очередь есть, но по ней ходит ровно одно сообщение, и
это сообщение ничего не стоит: потеря `reservation.expire` стоит задержки, а не
денег.

Под-проект 5 закрывает разделы 11, 12 и 20 `spec.md` — и делает это на одном
основании: **до сих пор в системе не было ни одной операции, которую нельзя
повторить**. Холд можно взять снова, отмену можно повторить, истечение можно
досчитать лениво. Списание денег — первая операция, у которой повтор имеет цену.
Всё остальное в этом под-проекте следует из этого факта:

- `Idempotency-Key` нужен не потому, что он есть в разделе 12, а потому, что
  ответ провайдера теряется в сети, а списание — нет;
- circuit breaker нужен не потому, что он есть в разделе 20, а потому, что для
  провайдера **нет запасного пути**: Redis и брокер можно обойти (ADR 0018,
  ADR 0029), а «считать, что оплата прошла» — нельзя;
- платёж уходит в очередь не потому, что RabbitMQ уже подключён, а потому, что
  Definition of Done проекта требует ровно этого: «payment обробляється
  асинхронно через RabbitMQ».

ADR 0013 отложил `bookings`, `payments` и `tickets` с явной формулировкой: форма
брони определяется тем, как работает платёж, а платёж — под-проект 5. Этот
под-проект обязан эту форму назвать.

### Швы, оставленные под-проектом 4

| Шов                                                          | Что с ним делает под-проект 5                                                  |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `PENDING → CONFIRMED` как единственный шов для платежа        | Открывается: между ними появляется `PAYMENT_PENDING`                            |
| `cinema.commands` и `assertTopology` как место для сообщений  | `payment.requested` биндится к тому же exchange, лестница копируется по форме   |
| `publishExpire` как шов для outbox                            | Порядок инвертируется: публикация **до** коммита, см. §5                        |
| TTL-гомогенность `reservation.expire.wait` (ADR 0024)         | Не нарушается: `reservations.expires_at` не переписывается никогда              |
| `releaseStaleHolds` как авторитетное ленивое истечение        | Получает второе плечо — для зависшего `PAYMENT_PENDING`                         |
| Fail open у Redis и брокера (ADR 0018, ADR 0029)              | Не оборачивается брекером: у обоих есть запасной путь, у провайдера — нет       |
| `settleExpired` — системное действие без сессии               | `PaymentConsumer` — второе такое действие, и первое, которое тратит деньги      |
| `reservation.expire.dlq` как первая метрика                   | Рядом встаёт `payment.requested.dlq`                                            |
| `uuidv7()` в приложении                                       | Даёт `payments.id` до коммита — то есть до того, как существует ключ идемпотентности |

### Принятые решения верхнего уровня

| Вопрос                                  | Решение                                                                          |
| --------------------------------------- | -------------------------------------------------------------------------------- |
| Синхронный или асинхронный платёж       | Асинхронный: `confirm` отвечает `202` и `PAYMENT_PENDING`                         |
| Какие таблицы добавляются               | Одна: `payments`. `bookings` и `tickets` не создаются (ADR 0034)                  |
| Где живёт фейковый провайдер            | Отдельный сервис Compose, реальный HTTP-хоп (ADR 0040)                            |
| Где применяется идемпотентность          | Структурно на границе API, `Idempotency-Key` — на вызове провайдера (ADR 0035)    |
| Кто владеет местами во время оплаты      | Платёж. Часы холда останавливаются (ADR 0036)                                     |
| Порядок публикации                      | До коммита, в отличие от `reservation.expire` (ADR 0037)                          |
| Что оборачивает circuit breaker          | Только провайдера, состояние в процессе воркера (ADR 0038)                        |
| Отказ провайдера                        | Не fail open. Ретрай по лестнице, затем `PAYMENT_FAILED` и освобождение мест      |
| Выбор режима                            | `PAYMENT_MODE=off\|queue`, по умолчанию `off`                                     |
| Новые рантайм-зависимости               | Нет. `fastify` уже в lockfile, `fetch` — глобальный в Node 24                     |
| Фронтенд                                | Меняется: опрос до терминального состояния                                        |
| Результат под-проекта                   | Набор тестов с внедрением отказов, не измерение                                   |

## 2. Цель и границы

### Цель

Провести деньги через систему так, чтобы ни один из четырёх сценариев провайдера
(`SUCCESS`, `FAILED`, `TIMEOUT`, `500`) не приводил ни к двойному списанию, ни к
подтверждённой брони без оплаты, ни к местам, застрявшим за незавершённым
платежом. Доказать это тестами, а не рассуждением.

Отдельная цель, названная в `spec.md` §11 как «особливо важливий кейс»:

```
Payment → SUCCESS
             ↓
       response lost
```

Эта ветка должна быть не обработана, а **невозможна**: повтор с тем же
`Idempotency-Key` обязан вернуть исходный результат, а не списать второй раз.

### В рамках

1. Таблица `payments` и два новых состояния брони.
2. `POST /reservations/:id/confirm` переводит холд в `PAYMENT_PENDING`, создаёт
   строку платежа, публикует `payment.requested` и отвечает `202`.
3. Очередь `payment.requested` с лестницей ретраев и DLQ на том же exchange.
4. `PaymentConsumer` во втором процессе-воркере, с собственным каналом и prefetch.
5. `apps/payment-provider` — отдельный сервис: `POST /charge`, идемпотентность по
   ключу, четыре сценария, управляемые заголовком или вероятностями.
6. `CircuitBreaker` как чистая единица с внедрённым временем, поверх клиента
   провайдера.
7. Второе плечо `releaseStaleHolds` для зависшего `PAYMENT_PENDING`.
8. Фронтенд: состояние «идёт оплата» и опрос до терминального статуса.
9. `PAYMENT_MODE=off` как режим, в котором поведение системы совпадает с
   под-проектом 4 построчно.

### Вне рамок

| Не делаем                                          | Почему                                                                                              |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `bookings` и `tickets`                              | Бронь уже несёт сессию, места, цены и сумму. Вторая таблица повторила бы это без нового инварианта (ADR 0034) |
| Возврат средств (`/void`, `/refund`)                | Появляется вместе с деньгами, которые нужно возвращать: см. §10, известное ограничение                |
| Транзакционный outbox                               | Публикация до коммита закрывает ту же дыру дешевле; outbox — под-проект, где сообщений станет больше |
| Общий брекер для Redis и брокера                    | У обоих есть запасной путь; одна абстракция поверх двух разных форм не подходит ни одной (ADR 0038)  |
| Хранилище ключей идемпотентности (`idempotency_keys`) | Путь `POST /reservations/:id/confirm` уже уникально называет операцию (ADR 0035)                     |
| Настоящий платёжный провайдер                       | Проект изучает механику, а не интеграцию                                                             |
| Аутентификация владельца платежа                    | ADR 0012 всё ещё в силе: сессия анонимна                                                             |
| Метрики Prometheus                                  | Под-проект 10. Счётчики выставляются наружу геттерами, как `ExpirePublisher.failureCount`             |

## 3. Модель данных

```sql
CREATE TABLE payments (
  id             uuid PRIMARY KEY DEFAULT uuidv7(),
  reservation_id uuid NOT NULL UNIQUE REFERENCES reservations(id),
  status         text NOT NULL,
  amount_cents   integer NOT NULL,
  provider_ref   text,
  attempts       integer NOT NULL DEFAULT 0,
  scenario       text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  settled_at     timestamptz,
  CONSTRAINT payments_status_check
    CHECK (status IN ('PENDING', 'SUCCEEDED', 'DECLINED', 'FAILED'))
);
```

Разбор колонок, каждая из которых существует по названной причине:

- **`reservation_id UNIQUE`** — структурная половина идемпотентности. Пять
  одновременных `confirm` сериализуются на `FOR UPDATE` брони, но индекс делает
  вторую вставку невозможной даже если бы блокировка когда-нибудь оказалась
  неверной. Это тот же приём, что `reservation_seats_active_uq` в под-проекте 2
  (ADR 0009): инвариант живёт в схеме, а не в коде, который его соблюдает.
- **`status`** — `DECLINED` и `FAILED` различаются намеренно. `DECLINED` —
  мнение провайдера («карта не прошла»), `FAILED` — наше решение прекратить
  попытки. Оба ведут бронь в `PAYMENT_FAILED`, но в DLQ и в метриках это разные
  события, и склеивать их значит терять единственный сигнал о том, что сломан
  downstream, а не карта.
- **`amount_cents`** — копия `reservations.total_price_cents` на момент создания
  платежа. Не денормализация ради скорости: это сумма, на которую был выставлен
  запрос провайдеру, и она обязана пережить любое последующее изменение брони.
- **`provider_ref`** — `NULL`, пока провайдер не ответил. Первое, что спросит
  человек, разбирающий DLQ.
- **`attempts`** — число обращений к провайдеру. Не дублирует `x-attempt`:
  заголовок живёт в сообщении и исчезает вместе с ним, колонка остаётся в базе.
- **`scenario`** — сквозной параметр фейкового провайдера, `NULL` в обычной
  работе. Живёт в базе, потому что попытка 2 обязана отправить тот же сценарий,
  что попытка 1, а сообщение несёт только идентификатор (§6).
- **`settled_at`** — момент перехода в терминальный статус. `created_at` и
  `settled_at` вместе дают длительность платежа, то есть первую величину, ради
  которой под-проект 10 придёт сюда.

Таблица `payments` попадает в экспортируемый `schema`, миграция добавляет её и
расширяет `reservations_status_check` двумя значениями.

## 4. Состояния брони

```
PENDING ──► PAYMENT_PENDING ──► CONFIRMED
   │              │
   │              └──────────► PAYMENT_FAILED
   ├──► CANCELLED
   └──► EXPIRED
```

`TRANSITIONS` в `state-machine.ts` получает:

```ts
PENDING:          ['PAYMENT_PENDING', 'CANCELLED', 'EXPIRED'],
PAYMENT_PENDING:  ['CONFIRMED', 'PAYMENT_FAILED'],
PAYMENT_FAILED:   [],
```

Три следствия, каждое из которых — решение, а не побочный эффект:

**`PENDING` получает две цели, а не одну.** Граф разрешает и
`PAYMENT_PENDING`, и `CONFIRMED`; какое ребро использовать, решает `confirm` по
`PAYMENT_MODE`. Соблазн сделать сам граф зависимым от конфигурации отвергнут:
`state-machine.ts` сегодня не импортирует ничего, кроме типа из контрактов, и
таблица разрешённых переходов — это описание домена, а не поведения процесса.
Разрешённое, но неиспользуемое ребро ничего не стоит; таблица переходов, у
которой два вида в зависимости от окружения, стоит ровно того, что её больше
нельзя прочитать как утверждение о домене.

**У `PAYMENT_PENDING` нет ребра ни в `EXPIRED`, ни в `CANCELLED`.** Это и есть
«платёж владеет строкой», выраженное в графе, а не в комментарии.
`DELETE /reservations/:id` во время оплаты отвечает `409`: пользователь не может
забрать места из-под операции, которая уже могла списать деньги.

**`PAYMENT_FAILED` терминален и освобождает места.** Отклонённая карта стоит
холда; повторная попытка — это новый холд. Альтернатива (`PAYMENT_FAILED →
PENDING` внутри остатка холда) вводит цикл в граф, который до сих пор был
ациклическим, и требует собственной границы числа попыток поверх лестницы
ретраев — двух счётчиков вместо одного. Решение записано в ADR 0039 вместе с
этой ценой.

## 5. Публикация: до коммита, в отличие от под-проекта 4

`publishExpire` работает **после** коммита и не бросает исключений (ADR 0029):
места уже держатся, строка уже записана, а ленивое истечение вернёт место в пул
независимо от того, дошло ли сообщение. У сообщения есть полноценная замена.

У `payment.requested` замены нет. Потерянное сообщение оставляет бронь в
`PAYMENT_PENDING` без единого процесса, который что-либо о ней знает. Поэтому
порядок инвертируется:

```
BEGIN
  SELECT ... FOR UPDATE                   -- бронь
  проверить canTransition(status, 'PAYMENT_PENDING')
  UPDATE reservations SET status = 'PAYMENT_PENDING'
  INSERT INTO payments (...) RETURNING id
  publish payment.requested { paymentId }  -- с подтверждением, таймаут 200 мс
COMMIT
```

Асимметрия безопасна ровно в одну сторону, и это единственная причина, по
которой такой порядок допустим:

- **Опубликовали, затем откатились.** Сообщение ссылается на `payments.id`,
  которого нет. Потребитель отправляет его на лестницу и в конце концов в DLQ
  (§5.1). Стоимость — одна запись в DLQ, которую человек должен опознать как
  безобидную.

- **Опубликовали, затем закоммитили — но потребитель успел раньше.** Это третий
  случай, и его не было в первой редакции этой спеки. См. §5.1.
- **Закоммитили, затем потеряли публикацию.** Бронь в `PAYMENT_PENDING`, места
  заняты, никто ничего не сделает до реаперa из §9. Стоимость — холд.

Первое дешевле второго, и порядок выбирается по этому неравенству. Отказ
публикации откатывает транзакцию, бронь остаётся `PENDING`, пользователь
получает `503` и может повторить `confirm` — места всё ещё его.

### 5.1. Гонка публикации и коммита

Публикация до коммита порождает случай, который первая редакция этой спеки
пропустила, а реализация обнаружила и **измерила**: окно порядка 2 мс на
локальном брокере.

Потребитель может забрать сообщение и прочитать `payments` **до того, как
транзакция-производитель закоммитила**. `claimPayment` вернёт `not-found` — и
это неотличимо от настоящего отката. Если потребитель на этом основании
подтверждает и выбрасывает сообщение, бронь через мгновение коммитится в
`PAYMENT_PENDING`, и о ней не знает ни один процесс. Это ровно тот повисший
холд, ради предотвращения которого публикация и была перенесена внутрь
транзакции: дыра, закрытая с одной стороны, открылась с другой.

Решение состоит из двух частей:

1. **Короткое локальное ожидание.** Потребитель повторяет чтение строки
   несколько раз с интервалом в десятки миллисекунд. Быстрый коммит
   разрешается здесь, без задержки лестницы.
2. **По исчерпании ожидания — на ступень, а не в ack.** Окно ожидания нельзя
   выбрать достаточно большим: этот проект существует ради сценария, где за
   один сеанс борются тысячи покупателей, и коммит дольше 180 мс там —
   обыденность, а не экзотика. Поэтому `not-found`, переживший ожидание,
   считается временным и уходит на следующую ступень; через секунды транзакция
   заведомо либо закоммичена, либо откачена.

Настоящий откат в результате доходит до `payment.requested.dlq`. Это принято
сознательно: откат **после** публикации почти недостижим, потому что публикация
— последний оператор транзакции `confirm`, так что его порождает практически
только сбой самого коммита. Видимая запись в DLQ лучше невидимо потерянного
сообщения.

Цена решения названа честно: обращение к брокеру (не более
`RABBITMQ_PUBLISH_TIMEOUT_MS`) происходит под блокировкой одной строки. Это одна
строка, а не диапазон, и таймаут ограничен сверху — но это именно тот шов, где
транзакционный outbox однажды заменит публикацию, и ADR 0037 это фиксирует.

Тело сообщения — `{ paymentId }`. Идентификатор и ничего больше, по тем же
причинам, что и в ADR 0027: сообщение, не несущее фактов, не может нести
устаревшие. Сумма, сценарий и состояние читаются из строки в момент обработки.

## 6. Идемпотентность

Раздел 12 `spec.md` требует: пять одинаковых запросов дают одну бронь, один
платёж, один билет. Этот под-проект добивается этого двумя разными механизмами
на двух разных границах, и различие между ними — содержание ADR 0035.

### На границе API — структурно, без ключа

Пять `POST /reservations/:id/confirm` сериализуются на `SELECT ... FOR UPDATE`
брони. Первый проходит `canTransition(PENDING, PAYMENT_PENDING)`, остальные
четыре видят `PAYMENT_PENDING` и возвращают текущее состояние с `202` — не
ошибку, потому что запрошенное уже происходит. `payments.reservation_id UNIQUE`
страхует это на уровне схемы.

Заголовок `Idempotency-Key` на этой границе не вводится сознательно. Операция
уже названа уникально: путь содержит идентификатор брони, а бронь может
оплачиваться только один раз. Ключ добавил бы второй идентификатор той же
операции, вместе с вопросом «а что если тот же ключ пришёл для другой брони» —
то есть новую ошибку, которой сейчас нет.

### На границе провайдера — ключом, потому что иначе нельзя

Здесь операция **не** адресуема: `POST /charge` создаёт списание, а не изменяет
названный ресурс. Единственный способ отличить повтор от второго платежа —
предъявить один и тот же ключ. Ключ — `payments.id`, сгенерированный `uuidv7()`
в приложении один раз при создании строки и потому стабильный на всех ступенях
лестницы:

```
attempt 1  POST /charge  Idempotency-Key: 0192f3...  → таймаут клиента (провайдер списал)
attempt 2  POST /charge  Idempotency-Key: 0192f3...  → 200 SUCCEEDED, X-Idempotent-Replay: true
                                                        тот же provider_ref
```

Это и есть кейс `spec.md` §11. Он разрешается не обработкой ошибки, а тем, что
второе списание невозможно: провайдер хранит ответ по ключу и повторяет его.

`attempts` в строке платежа растёт на каждой попытке, включая повторы — иначе
из базы нельзя отличить платёж, прошедший с первого раза, от прошедшего с
третьего.

## 7. Потребление

`PaymentConsumer` живёт в том же процессе-воркере, что `ExpireConsumer`
(ADR 0028): та же вторая точка входа того же образа, свой канал, свой prefetch,
своя подписка, переустанавливаемая на событии `connect`. Ожидание ответа
провайдера асинхронно, поэтому один event loop обслуживает обе очереди без
голодания.

### Таблица решений

| Условие                                  | Что делаем                                                                     | Сообщение     |
| ---------------------------------------- | ------------------------------------------------------------------------------ | ------------- |
| Тело не разбирается                       | Ничего                                                                          | сразу в DLQ   |
| Строки платежа нет                        | Короткое ожидание (§5.1), затем на ступень: строка может быть ещё не видна       | ретрай        |
| `payments.status ≠ PENDING`               | Ничего. Повтор доставки уже учтён                                               | ack           |
| Бронь не в `PAYMENT_PENDING`              | Ничего. Строку увёл реапер или конкурирующая доставка                           | ack           |
| Провайдер → `SUCCEEDED`                   | `payments → SUCCEEDED`, бронь → `CONFIRMED`, `retain` ключей мест               | ack           |
| Провайдер → `DECLINED`                    | `payments → DECLINED`, бронь → `PAYMENT_FAILED`, места и ключи освобождаются     | ack           |
| Таймаут, 5xx, отказ соединения, брекер OPEN | Ничего в базе, кроме `attempts`                                                  | следующая ступень |
| Ступени исчерпаны                         | `payments → FAILED`, бронь → `PAYMENT_FAILED`, места освобождаются               | DLQ           |

Четыре верхние строки — та же структурная идемпотентность, что у `settleExpired`
(ADR 0027): состояние перечитывается, тело не используется как источник фактов.

**Порядок «опубликовать, затем подтвердить»** сохраняется дословно из
под-проекта 4: дубликат поглощается проверкой статуса, потеря — нет.

**Исчерпание ступеней завершает бронь, а не только сообщение.** Сообщение
уходит в DLQ для человека, но места возвращаются в пул немедленно: оставить их
до разбора DLQ значит продавать зал по скорости реакции дежурного. Строка
платежа при этом `FAILED`, и в DLQ лежит именно то сообщение, которое к этому
привело.

**`retain`, а не `release`, при успехе** — по причине из под-проекта 3:
подтверждённое место никогда не освобождается, и снятие ключа только пригласило
бы следующий запрос взять блокировку, открыть транзакцию и получить отказ от
индекса.

## 8. Circuit breaker

`CircuitBreaker` — чистая единица в `apps/api/src/resilience/`: без HTTP, без
Nest, с внедрённым `now()`. Всё её поведение проверяется юнит-тестом с
поддельными часами, без единого контейнера.

```
CLOSED ──(N подряд отказов)──► OPEN
OPEN ──(прошло openMs)──► HALF_OPEN
HALF_OPEN ──(один успех)──► CLOSED
HALF_OPEN ──(один отказ)──► OPEN
```

Три решения, определяющие её ценность:

**Отказ провайдера — не отказ вызова.** `DECLINED` — успешный вызов с
отрицательным ответом, и он **не** приближает брекер к открытию. Считаются
только таймауты, 5xx и отказы соединения. Обратное поведение открывало бы брекер
на потоке честных отказов карты, то есть отключало бы платежи ровно тогда, когда
система работает правильно.

**Открытый брекер бросает исключение, а не возвращает ошибку.** Исключение
попадает в тот же `catch`, что таймаут, и сообщение уходит на следующую ступень
лестницы. Брекер не изобретает собственную задержку — она уже есть в топологии;
он только избавляет мёртвый downstream от запросов. Это и есть причина, по
которой брекер и лестница ретраев не дублируют друг друга: лестница решает
*когда* повторить, брекер — *стоит ли вообще звонить*.

**Состояние — в процессе, не в Redis.** Три воркера означают три независимых
брекера, каждый учится на своём трафике. Общее состояние в Redis защитило бы
флот целиком, но поставило бы Redis на путь платежа и потребовало бы ответа на
вопрос «а что если состояние брекера недоступно» — на который единственный
честный ответ, fail open, делает брекер бесполезным ровно тогда, когда он нужен.
Цена локального решения (до N×порог лишних запросов к мёртвому провайдеру)
названа в ADR 0038.

## 9. Гонка истечения: кто владеет местами

Сценарий, ради которого этот раздел существует. Холд истекает в 10:00,
пользователь подтверждает в 9:50, провайдер отвечает медленно; одна только
лестница ретраев — 155 секунд.

**Часы холда останавливаются.** Переход в `PAYMENT_PENDING` передаёт строку
платежу. `reservations.expires_at` **не переписывается никогда** — это прямое
следствие ADR 0024: `reservation.expire.wait` работает правильно только потому,
что все холды имеют один TTL и порядок публикации равен порядку истечения.
Продление холда потребовало бы пересоздания очереди; вместо этого меняется не
срок, а то, кто за него отвечает.

Три механизма приводятся в соответствие:

1. **`settleExpired`** получает правило: бронь в `PAYMENT_PENDING` возвращает
   `awaiting-payment`, сообщение подтверждается и отбрасывается. Это корректно,
   потому что у платежа есть собственная граница — не потому, что истечение
   «когда-нибудь потом».
2. **Граница платежа** — сам платёж: `SUCCEEDED` ведёт в `CONFIRMED`,
   исчерпание ступеней — в `PAYMENT_FAILED` с освобождением мест. Обе ветки
   завершаются за время, ограниченное лестницей.
3. **Реапер зависших платежей.** Остаётся один незакрытый случай: сообщение
   дошло до DLQ или воркер умер, держа его. `releaseStaleHolds` получает второе
   плечо — бронь в `PAYMENT_PENDING`, чей платёж старше
   `PAYMENT_DEADLINE_SECONDS`, переводится в `PAYMENT_FAILED`, места
   освобождаются.

Третий пункт важнее, чем выглядит: он сохраняет ADR 0030 в силе. Ленивое
освобождение остаётся авторитетным механизмом возврата места в пул — теперь для
обоих способов, которыми холд может закончиться, а очередь остаётся
оптимизацией. Ни один путь возврата места не зависит от того, работает ли
брокер.

Симметрично: `settleExpired` возвращает `awaiting-payment` **только** для
`PAYMENT_PENDING`; `PAYMENT_FAILED` попадает в существующую ветку `terminal` без
изменений.

## 10. Фейковый провайдер

`apps/payment-provider` — отдельный рабочий пакет: Fastify, без базы, без Nest,
без Drizzle. Отдельный сервис Compose, отдельный образ, отдельный жизненный цикл
— чтобы «провайдер лёг» проверялось остановкой контейнера, а не подменой объекта.

Тот же довод, что ADR 0007 привёл для Testcontainers вместо моков: таймаут,
реализованный `setTimeout` в собственном процессе, — не таймаут, и брекер,
никогда не видевший зависшего сокета, не продемонстрирован.

### Контракт

```
POST /charge
Idempotency-Key: <uuid>            обязателен
X-Payment-Scenario: <сценарий>     необязателен
{ "amountCents": 4500, "reference": "<reservationId>" }

200 { "status": "SUCCEEDED", "providerRef": "ch_...", "amountCents": 4500 }
200 { "status": "DECLINED",  "declineReason": "insufficient-funds" }
500 { ... }                        сценарий error
—                                  сценарий timeout: ответ не приходит
```

Схемы живут в `packages/contracts/src/payment.ts` и используются обеими
сторонами: провайдер валидирует вход, клиент разбирает ответ. Это ADR 0003,
применённый ко второму HTTP-контракту в проекте.

### Сценарии

Заголовок задаёт исход точно; без него применяются настраиваемые вероятности.
Тесты называют сценарий и получают детерминизм; демонстрационный стек оставляет
заголовок пустым и получает реалистичный смешанный трафик. Ветки «только для
тестов» в продакшн-коде при этом не возникает: провайдер целиком — фейк, и
сценарий для него обычный вход.

| Сценарий  | Поведение                                                       |
| --------- | ---------------------------------------------------------------- |
| `success` | `200 SUCCEEDED`                                                   |
| `decline` | `200 DECLINED`                                                    |
| `error`   | `500`                                                             |
| `timeout` | Ответ откладывается на `PROVIDER_HANG_MS`, заведомо больше таймаута клиента |

### Идемпотентность провайдера

`Map` в памяти: ключ → сохранённый ответ. Повтор отдаёт сохранённый ответ и
`X-Idempotent-Replay: true`. Хранилище в памяти достаточно, потому что
перезапуск провайдера — это перезапуск «банка», а не потеря нашей брони; тесты,
проверяющие повтор, работают против одного экземпляра.

**Важно для сценария `timeout`:** ответ сохраняется в момент, когда решение
принято, а не когда оно отправлено. Иначе повтор после потерянного ответа не
нашёл бы записи — и кейс `spec.md` §11 не воспроизводился бы, потому что
провайдер вёл бы себя неправдоподобно честно.

### Известное ограничение

Если все попытки не дошли до провайдера, платёж помечается `FAILED`. Если при
этом первая попытка всё же списала деньги, а ответ был потерян навсегда, система
об этом не узнает. Стабильный `Idempotency-Key` делает этот случай крайне
маловероятным — каждая следующая попытка предъявляет тот же ключ и получает
сохранённый `SUCCEEDED`, — но не невозможным. Закрывает его компенсация
(`/void`), и она относится к под-проекту, в котором появятся возвраты.

## 11. Топология развёртывания

```
                 ┌─────────┐
   браузер ──────┤  nginx  ├──── api ×3 ─────┐
                 └─────────┘                 │
                                             ├──► postgres
                       worker ───────────────┤
                         │                   ├──► redis
                         │                   │
                         └──► payment-provider└──► rabbitmq
```

Провайдер не публикует порт наружу и не проходит через nginx: его единственный
клиент — воркер. Compose получает сервис `payment-provider` с healthcheck;
`worker` зависит от него. `API_REPLICAS` не касается ни воркера, ни провайдера.

`reservation.expire` и `payment.requested` делят один exchange
`cinema.commands` и одну функцию `assertTopology` — по причине, названной в
под-проекте 4: повторное объявление очереди с другими аргументами убивает канал,
поэтому объявление обязано быть в одном месте.

```
cinema.commands (direct, durable)
├── reservation.expire.wait      x-message-ttl → reservation.expire
├── reservation.expire
├── reservation.expire.retry.{1,2,3}
├── reservation.expire.dlq
├── payment.requested                        ◄ новое
├── payment.requested.retry.{1,2,3}          ◄ новое
└── payment.requested.dlq                    ◄ новое
```

Очереди ожидания у платежа нет: первая попытка списания не откладывается.

`nextHop` в `retry.ts` сегодня зашит на ключи истечения (`retryKey`,
`EXPIRE_DEAD_KEY`). Он обобщается до параметра-лестницы `{ retryKey, deadKey }`
— точечное изменение существующего кода, которое требуется именно этой задачей,
а не рефакторинг по случаю.

## 12. Конфигурация

| Переменная                          | По умолчанию | Смысл                                                       |
| ----------------------------------- | ------------ | ------------------------------------------------------------ |
| `PAYMENT_MODE`                      | `off`        | `off` — поведение под-проекта 4 построчно; `queue` — платёж   |
| `PAYMENT_PROVIDER_URL`              | нет          | Обязателен при `queue`. Без значения по умолчанию — сознательно |
| `PAYMENT_TIMEOUT_MS`                | `2000`       | Порог, после которого медленный провайдер считается мёртвым   |
| `PAYMENT_DEADLINE_SECONDS`          | `300`        | После этого зависший `PAYMENT_PENDING` реапится                |
| `PAYMENT_BREAKER_FAILURE_THRESHOLD` | `5`          | Отказов подряд до открытия                                    |
| `PAYMENT_BREAKER_OPEN_MS`           | `30000`      | Сколько брекер держится открытым до `HALF_OPEN`                |

`RABBITMQ_RETRY_DELAYS_MS` переиспользуется обеими лестницами: одна ручка вместо
двух, и обе очереди меняются согласованно.

`refine` добавляется по образцу существующих: `PAYMENT_MODE=queue` требует
`PAYMENT_PROVIDER_URL` и `RABBITMQ_URL`. Отсутствие значения по умолчанию у URL
— то же решение, что у `REDIS_URL` и `RABBITMQ_URL` (ADR 0018): значение по
умолчанию делает проверку бессодержательной, а отказ стартовать лучше, чем `500`
на каждый запрос.

`off` по умолчанию — третье применение правила «новая подсистема не включает
себя сама» (ADR 0017, затем `RESERVATION_EXPIRY_MODE`). Здесь у него есть
дополнительная причина: в `off` граф состояний сохраняет ребро
`PENDING → CONFIRMED`, и все тесты под-проектов 1–4 остаются верными без правок.

## 13. Фронтенд

`confirm` теперь может ответить `202` вместо `200`, и приложение обязано это
различать — иначе оно молча объявит оплаченным то, что ещё не оплачено.

Страница брони получает четвёртое состояние — «идёт оплата» — и опрос через
`refetchInterval` TanStack Query, включённый ровно пока статус
`PAYMENT_PENDING`. Терминальные исходы:

| Статус           | Что видит пользователь                                  |
| ---------------- | -------------------------------------------------------- |
| `CONFIRMED`      | Подтверждение с местами (как сегодня)                    |
| `PAYMENT_FAILED` | Оплата не прошла, места освобождены, кнопка выбрать снова |
| `EXPIRED`        | Холд истёк (как сегодня)                                 |

Опрос останавливается на терминальном статусе — интервал не остаётся включённым
на подтверждённой брони. URL остаётся источником состояния UI, Zustand не
появляется (ADR 0014).

## 17. Definition of Done

1. `npm run lint`, `npm run typecheck`, `npm test` — зелёные на Node 24.
2. Полный набор тестов зелёный в обоих режимах: `PAYMENT_MODE=off` и
   `PAYMENT_MODE=queue`.
3. `docker compose up --build` поднимает стек с провайдером; воркер потребляет
   обе очереди.
4. Пять одновременных `confirm` одной брони дают одну строку `payments`.
5. Сценарий `timeout` с последующим повтором даёт **одно** списание и тот же
   `provider_ref`.
6. Остановка контейнера провайдера открывает брекер; API продолжает отвечать
   `202` на `confirm`, места возвращаются в пул через `PAYMENT_FAILED`.
7. Исчерпание ступеней кладёт сообщение в `payment.requested.dlq` и освобождает
   места.
8. `reservation.expire`, доставленное во время `PAYMENT_PENDING`, не забирает
   места.
9. Playwright-smoke проходит через nginx до подтверждённой брони.
10. Восемь ADR записаны; README отражает под-проект 5.

## 18. Что этот под-проект оставляет следующему

- **`payments` — первая таблица, где строка означает деньги.** Возвраты,
  выплаты и билеты вешаются на неё, и `provider_ref` — то, чем они будут
  оперировать.
- **Публикация до коммита — это outbox без таблицы.** Она закрывает потерю
  сообщения ценой брокера под блокировкой строки. Когда сообщений станет
  больше одного за транзакцию, эта цена перестанет окупаться, и `uuidv7()`
  уже готов давать идентификаторы строкам outbox.
- **Брекер существует и умеет считать.** `state` и счётчики выставлены
  геттерами; под-проект 10 снимает их вместе с глубинами `payment.requested`
  и `payment.requested.dlq` и распределением `x-attempt`.
- **Компенсация не написана.** §10 называет единственный сценарий, в котором
  деньги списаны, а брони нет. Возвраты — первый пункт, который его закроет.
- **`PAYMENT_FAILED` терминален.** Если продуктовое решение изменится, менять
  придётся граф состояний, а не только UI: ADR 0039 записывает, что цикл был
  отвергнут осознанно.
- **Три брекера вместо одного.** Общее состояние во внешнем хранилище — первое,
  что стоит пересмотреть, когда воркеров станет заметно больше трёх.
- **Домены событий готовы.** `payment.succeeded` и `payment.failed` — очевидные
  первые события для Kafka в под-проекте 6, и `PaymentService` — единственное
  место, откуда они должны публиковаться.
