## 1. Контекст

Под-проект 3 закончен: совещательная блокировка в Redis стоит перед транзакцией,
инвариант остался в частичном уникальном индексе, обе стратегии живут в одной
сборке, и цифры записаны в `docs/experiments/2026-08-28-db-vs-redis-locking.md`.

Под-проект 4 закрывает разделы 9 и 10 `spec.md`. RabbitMQ входит в систему не
потому, что он есть в списке технологий, а потому, что у ленивого истечения
(ADR 0011) есть названная граница: **истечение холда не является событием**.
Строка `PENDING` с прошедшим `expires_at` не переходит в `EXPIRED` сама — её
переводит следующий, кто захотел эти места. Пока никто не захотел, ничего не
происходит. Это корректно для карты мест (предикат истечения применяется на
каждом чтении), но означает, что момент «холд истёк» не существует как факт, на
который можно подписаться.

Под-проект 5 добавит платёж, и там этот момент понадобится по-настоящему:
истечение неоплаченного холда — это то, о чём нужно уведомить, что нужно
отменить у провайдера и что нужно посчитать. Под-проект 4 обязан сделать
истечение наблюдаемым событием, **не сделав очередь обязательной для
корректности**.

ADR 0022 уже зафиксировал, почему TTL ключа Redis не мог стать этой заменой:
истечение ключа ничего не пишет в PostgreSQL, а PostgreSQL — источник истины.
Сообщение `reservation.expire` пишет.

### Швы, оставленные под-проектом 3

| Шов                                                          | Что с ним делает под-проект 4                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------------ |
| `releaseStaleHolds` как авторитетное ленивое истечение        | Остаётся авторитетным. Воркер — второй путь к тому же результату   |
| `uuidv7()` в приложении                                       | Даёт `messageId` до того, как существует сообщение                 |
| Три реплики API за nginx                                      | Предпосылка: конкурирующие потребители имеют смысл только здесь     |
| `LOCK_STRATEGY` как переключатель подсистемы (ADR 0017)       | Копируется как `RESERVATION_EXPIRY_MODE`                            |
| Fail open при отказе Redis (ADR 0018)                         | Копируется дословно для брокера                                     |
| `PENDING → CONFIRMED` как шов для платежа                     | Не трогаем: это под-проект 5                                        |
| Отсутствие любого планировщика (ADR 0011)                     | Нарушается сознательно и в одну сторону: см. §3                     |

### Принятые решения верхнего уровня

| Вопрос                              | Решение                                                                |
| ----------------------------------- | ---------------------------------------------------------------------- |
| Какие сообщения ходят               | Ровно одно: `reservation.expire`                                        |
| Откуда берётся задержка в 10 минут  | Очередь без потребителя с `x-message-ttl` и dead-letter exchange        |
| Тело сообщения                      | Только `reservationId`. Никаких фактов, которые могут устареть          |
| Где живёт воркер                    | Тот же образ, вторая точка входа, отдельный сервис Compose              |
| Ретраи                              | Три очереди-ступени с фиксированным TTL каждая, счётчик в `x-attempt`   |
| Исчерпание попыток                  | `reservation.expire.dlq`, терминальная очередь без потребителя          |
| Брокер недоступен                   | Fail open: `201` уходит, ленивое истечение остаётся сетью безопасности  |
| Выбор режима                        | `RESERVATION_EXPIRY_MODE=lazy\|queue`, по умолчанию `lazy`              |
| Клиент                              | `amqplib` 2, единственная новая рантайм-зависимость                     |
| Результат под-проекта               | Набор тестов с внедрением отказов, не измерение                         |
| Фронтенд                            | Не меняется                                                             |

## 2. Цель и границы

### Цель

Сделать истечение холда доставленным сообщением, а не побочным эффектом чужого
запроса, и доказать тестами, что путь доставки выдерживает дубликаты, отказы
обработчика, ядовитые сообщения и падение брокера — **не став при этом
обязательным для того, чтобы место освободилось**.

Формулировка результата: на остановленном брокере система ведёт себя ровно как
под-проект 3. Это не деградация, которую приходится терпеть, а требование.

### В рамках

- Одно сообщение `reservation.expire` и его топология: exchange, шесть очередей,
  ключи маршрутизации, dead-lettering.
- Продюсер в `ReservationService.create`, после коммита.
- Отдельный процесс-воркер: вторая точка входа того же образа, контекст Nest без
  HTTP, конкурирующие потребители, `prefetch`.
- Идемпотентный обработчик: `settleExpired(reservationId)` под тем же `FOR UPDATE`,
  что уже берут `confirm` и `cancel`.
- Ограниченные ретраи с возрастающей задержкой и DLQ.
- Восстановление соединения и переустановка топологии после разрыва.
- Корректное завершение: незавершённые сообщения не теряются.
- `RESERVATION_EXPIRY_MODE=lazy|queue`; режим `lazy` сохраняет поведение
  под-проекта 3 без единой новой сетевой операции.
- Тесты с внедрением отказов на реальном брокере через Testcontainers.
- ADR под-проекта и обновление README.

### Вне рамок

Каждый пункт — с указанием, чей это под-проект:

| Вне рамок                                              | Чьё это                        |
| ------------------------------------------------------ | ------------------------------- |
| `booking.created`, `payment.requested`, `ticket.generate`, `email.send` | под-проект 5 и далее |
| Транзакционный outbox                                   | под-проект 5, вместе с деньгами |
| `Idempotency-Key` на HTTP                               | под-проект 5                    |
| Circuit breaker вокруг брокера и Redis                  | под-проект 5                    |
| Rate limiting                                           | под-проект 6                    |
| Kafka, доменные события, consumer groups                | под-проект 6                    |
| Prometheus, Grafana, метрики очереди                    | под-проект 10                   |
| Таблицы `bookings`, `payments`, `tickets`               | под-проект 5 (ADR 0013)         |
| Аутентификация                                          | не запланирована                |
| Изменения в `apps/web/src`                              | ничьё: фронтенд не меняется     |
| Приоритеты, отложенные плагины, quorum-очереди          | не нужны здесь; см. §3          |

**Единственная новая рантайм-зависимость — `amqplib`.** Если задача выглядит
так, будто ей нужна вторая, — остановиться и спросить.

## 3. Архитектура очереди

### Почему это не планировщик

ADR 0011 запретил cron, `setInterval` и любой sweeper, и этот запрет остаётся в
силе: воркер **не опрашивает базу**. Он не знает про `expires_at` до того, как
брокер вручит ему сообщение, и не имеет ни таймера, ни расписания. Работу
планирует брокер, по одному сообщению на холд, и делает это тем же механизмом
TTL, который очередь предоставляет как хранилище.

Разница существенная и её нужно назвать: sweeper сканирует таблицу в поисках
работы, которой может не быть; здесь работа адресована заранее и приходит сама.
Первое — это опрос, второе — доставка.

### Топология

Один прочный direct exchange `cinema.commands` и шесть прочных очередей. Каждый
переход — один и тот же механизм «TTL + dead-letter», использованный трижды: как
задержка, как отсрочка ретрая и как конец пути.

```
create() ── publish rk=reservation.expire.wait ──► [reservation.expire.wait]
                                                     без потребителя
                                                     x-message-ttl = TTL холда
                                                            │ expired
                                                            ▼ DLX → rk=reservation.expire
                                                    [reservation.expire] ◄────────┐
                                                     воркер, prefetch                │
                                                            │ обработчик бросил      │ expired
                                                            ▼ publish rk=…retry.N    │
                                    [retry.1 5s] [retry.2 30s] [retry.3 120s] ───────┘
                                                            │ попытки исчерпаны
                                                            ▼ publish rk=…dead
                                                    [reservation.expire.dlq]
                                                     терминальная, без TTL и DLX
```

| Очередь                      | Ключ привязки                 | Аргументы                                                                 |
| ---------------------------- | ----------------------------- | ------------------------------------------------------------------------- |
| `reservation.expire.wait`    | `reservation.expire.wait`     | `x-message-ttl` = `RESERVATION_TTL_SECONDS × 1000`, `x-dead-letter-exchange` = `cinema.commands`, `x-dead-letter-routing-key` = `reservation.expire` |
| `reservation.expire`         | `reservation.expire`          | нет                                                                        |
| `reservation.expire.retry.1` | `reservation.expire.retry.1`  | `x-message-ttl` = ступень 1, тот же DLX и DLRK                             |
| `reservation.expire.retry.2` | `reservation.expire.retry.2`  | `x-message-ttl` = ступень 2, тот же DLX и DLRK                             |
| `reservation.expire.retry.3` | `reservation.expire.retry.3`  | `x-message-ttl` = ступень 3, тот же DLX и DLRK                             |
| `reservation.expire.dlq`     | `reservation.expire.dead`     | нет — ни TTL, ни DLX                                                       |

### Решения и обоснования

**Очередь ожидания, а не плагин отложенных сообщений.** Ядро AMQP умеет ровно то,
что нужно, на стоковом образе `rabbitmq:4-management-alpine`. Плагин
`rabbitmq_delayed_message_exchange` требует собственного Dockerfile для брокера и
хранит отложенные сообщения вне очереди: их не видно как глубину, они иначе
переживают рестарт. Цена ядра — ограничение головы очереди (см. ниже), и это
ограничение здесь выполняется, а не игнорируется.

**Ограничение головы очереди — предусловие, а не дефект.** Очередь с
`x-message-ttl` истекает только голову: сообщение, срок которого прошёл, но перед
которым стоит более долгое, будет ждать. Для `reservation.expire.wait` это
безопасно **потому, что все холды имеют один и тот же TTL**, а значит порядок
публикации совпадает с порядком истечения. Это предусловие держится ровно до тех
пор, пока `RESERVATION_TTL_SECONDS` одинаков для всех броней. Если под-проект 5
введёт разные сроки холда — например, более длинный на время платежа — очередь
ожидания придётся заменить, и спека под-проекта 5 обязана это заметить.

**Ступени ретрая, а не одна очередь ретрая.** Возрастающая задержка внутри одной
очереди нарушила бы ровно то предусловие, которое мы только что приняли: сообщение
на 5 секунд встало бы за сообщением на 120. Одна очередь на ступень, TTL
фиксирован для каждой, головы блокируются только однородными соседями. Ступеней
три; их задержки задаются `RABBITMQ_RETRY_DELAYS_MS`, чтобы тесты гоняли их за
миллисекунды.

**Счётчик попыток — собственный заголовок `x-attempt`, а не `x-death`.** RabbitMQ
складывает записи `x-death` по паре «очередь + причина» и хранит в каждой `count`;
восстановить из этого номер попытки можно, но только зная, какие очереди являются
ступенями, и заново — при каждом изменении топологии. Заголовок, который пишем мы
сами, читается однозначно. `x-death` при этом логируется целиком: как история
маршрута он полезен, как управляющая переменная — хрупок.

Семантика счётчика фиксируется здесь, чтобы её не пришлось выводить из кода:
`x-attempt` — это **число уже состоявшихся неудачных обработок**. Продюсер
публикует `0`. Обработчик, упавший на сообщении с `x-attempt = n`, публикует его
с `x-attempt = n + 1` в ступень с индексом `n + 1`; когда `n + 1` превышает длину
`RABBITMQ_RETRY_DELAYS_MS`, сообщение уходит в DLQ. При трёх ступенях обработчик
вызывается не более четырёх раз.

**Direct exchange, а не topic.** Ключи здесь — точные имена, не образцы. Topic
понадобится, когда появится второй потребитель, которому нужен `reservation.*`;
сегодня такого нет, и wildcard был бы обещанием, которое некому исполнять.

**Классические очереди, а не quorum.** Quorum-очередь даёт `x-delivery-limit` и
DLQ без ступеней, но её повторная доставка немедленна — обработчик, падающий из-за
короткой недоступности базы, сожжёт весь лимит за миллисекунды. Отсрочка здесь
важнее, чем экономия трёх очередей. Репликация брокера в этом стеке отсутствует,
так что второе преимущество quorum тоже не оплачено.

**Ошибка `PRECONDITION_FAILED` заложена в устройство.** Повторное объявление
очереди с другими аргументами возвращает 406 и убивает канал. Поэтому топология
объявляется ровно в одном месте — `assertTopology(channel)` — и вызывается как из
старта воркера, так и из хука `setup` при переподключении, всегда с одними и теми
же аргументами. Следствие, которое нужно знать заранее: **изменение
`RESERVATION_TTL_SECONDS` или ступеней ретрая на живом стеке требует удаления и
пересоздания соответствующих очередей.** Это записано здесь, чтобы не быть
обнаруженным на дежурстве.

## 4. Публикация

### Где именно

В `ReservationService.create`, после коммита транзакции и после `releaseLocks`,
непосредственно перед `return`. Никогда внутри транзакции — по той же причине, по
которой внутри неё не снимаются блокировки: транзакция может откатиться,
опубликованное сообщение — нет.

### Сообщение

```
exchange:      cinema.commands
routing key:   reservation.expire.wait
body:          {"reservationId": "<uuid v7>"}
contentType:   application/json
messageId:     <тот же uuid брони>
correlationId: <traceId запроса>
timestamp:     <момент публикации>
persistent:    true
mandatory:     true
headers:       { "x-attempt": 0 }
```

**Тело несёт только идентификатор.** Ни `seatIds`, ни `expiresAt`, ни `showtimeId`.
Это и есть механизм идемпотентности: устаревшее сообщение не может нести
устаревшие факты, если оно не несёт фактов вообще. Обработчик перечитывает
состояние сам, поэтому подтверждение и отмена брони не обязаны ничего отменять в
очереди — сообщение просто найдёт терминальную строку.

**`mandatory: true` и confirm-канал.** Первое ловит ошибку топологии (сообщение,
которое некуда маршрутизировать, вернётся через `return`, а не исчезнет); второе
даёт подтверждение брокера, что сообщение принято. Оба нужны, потому что
публикация здесь молчаливая: её отказ не виден пользователю.

### Отказ публикации не проваливает запрос

Ошибка публикации, возврат `mandatory` и таймаут подтверждения
(`RABBITMQ_PUBLISH_TIMEOUT_MS`, по умолчанию 200 мс) логируются на `warn`,
увеличивают счётчик и **не влияют на ответ**: `201` уходит, места удержаны,
строка закоммичена, а ленивое истечение по-прежнему её уберёт. Это дословно
позиция ADR 0018, применённая ко второй необязательной подсистеме, и это же —
причина, по которой воркеру вообще разрешено существовать.

Из этого следует и то, чего здесь нет: **`/ready` не проверяет брокер**. Готовность
означает «PostgreSQL отвечает». Выводить реплики из ротации из-за подсистемы, без
которой сервис корректен, — это превращать проблему пропускной способности в
отказ.

## 5. Потребление

### Процесс

Вторая точка входа того же образа: `apps/api/src/worker/main.ts` поднимает
`NestFactory.createApplicationContext(WorkerModule)` — без HTTP-слушателя, без
таблицы маршрутов, без Swagger. `WorkerModule` импортирует существующие
`ConfigModule`, `DrizzleModule`, `LockingModule`, `CatalogModule` и
`ReservationModule` обычным импортом: ни один пакет не извлекается в `packages/`,
ни одна сборка не добавляется.

Процесс отдельный намеренно. Потребитель внутри реплик API делил бы с обслуживанием
запросов цикл событий, пул соединений и домен отказа — шторм ретраев стал бы
задержкой API, а измерения под-проекта 3 перестали бы быть сопоставимыми.

**При `RESERVATION_EXPIRY_MODE=lazy` воркер не работает, а завершается.** Он
пишет одну строку в лог на `info` и выходит с кодом `0`, не открывая ни
соединения с брокером, ни пула к базе. Сервис Compose при этом остаётся
объявленным — режим переключается переменной окружения, а не редактированием
стека, — и `restart` у него выставлен так, чтобы штатный выход не считался
падением. Это та же дисциплина, по которой `RedisModule` в под-проекте 3 отдаёт
`null` вместо клиента при стратегии `db`: выключенная подсистема не должна ни
подключаться, ни логировать, ни отличать базовый прогон от измеряемого.

### Таблица решений обработчика

Сообщение разбирается Zod-схемой; затем вызывается новый метод
`ReservationService.settleExpired(reservationId)`, берущий тот же `FOR UPDATE` на
строку брони, что уже берут `confirm` и `cancel`.

| Состояние                                    | Действие                                                       | Ack |
| -------------------------------------------- | -------------------------------------------------------------- | --- |
| Тело не разбирается схемой                   | Сразу в DLQ, без ретраев                                        | да  |
| Строки нет                                   | Ничего                                                          | да  |
| `CONFIRMED`, `CANCELLED` или `EXPIRED`       | Ничего                                                          | да  |
| `PENDING`, но `expires_at > now()`           | Ничего, запись в лог на `info`                                  | да  |
| `PENDING` и `expires_at <= now()`            | `EXPIRED`, `released_at` на местах, снятие ключей после коммита | да  |
| Обработчик бросил                            | Публикация в ступень `x-attempt`, затем ack оригинала           | да  |
| Обработчик бросил, попытки исчерпаны         | Публикация в DLQ, затем ack оригинала                           | да  |

**Ядовитое сообщение не ретраится.** Тело, которое не разобралось, не разберётся и
через тридцать секунд; ретрай только отсрочит диагноз. В DLQ оно уходит немедленно,
вместе с исходным телом и заголовками.

**Не наступивший срок — не ошибка.** `PENDING` с будущим `expires_at` означает, что
сообщение пришло раньше срока: TTL очереди считается от публикации, а `expires_at`
— часами базы, и это два разных источника времени. Ack и запись в лог; ленивое
истечение доведёт дело до конца, если сообщение больше не придёт.

**Идемпотентность структурная, а не учётная.** Доставка «хотя бы один раз»
безопасна потому, что вторая доставка находит терминальную строку и ничего не
делает. Ни таблицы обработанных сообщений, ни ключа дедупликации нет:
`Idempotency-Key` — это HTTP-проблема под-проекта 5, и она там и останется.

### Порядок «опубликовать, затем подтвердить»

При отказе обработчика сообщение сначала публикуется в следующую ступень, и только
потом подтверждается оригинал. Между этими двумя шагами есть окно: публикация
прошла, ack не прошёл — брокер доставит сообщение снова, и обработчик отработает
дважды. Это допущено сознательно: дубликат поглощается идемпотентностью выше, а
обратный порядок («ack, затем publish») терял бы сообщение при том же сбое.
Потерять хуже, чем повторить.

### Конкурирующие потребители и prefetch

`RABBITMQ_PREFETCH` (по умолчанию 20) ограничивает число неподтверждённых
сообщений на канал. Реплик воркера в Compose две — не для пропускной способности,
а чтобы конкурирующие потребители существовали и в тестах, и в стеке: одно
сообщение достаётся ровно одному потребителю, и это свойство должно быть видно, а
не подразумеваться.

### Переподключение и завершение

Соединение открывается через `connect(url, { recovery: { … } })`. Восстановление —
функция библиотеки начиная с `amqplib` 1.1.0: экспоненциальная задержка, джиттер и
предел попыток настраиваются, а хук `setup(model)` вызывается **после каждого
успешного подключения**. Именно в нём переобъявляется топология и заново
открывается потребитель, поэтому разрыв не требует ни одной строки собственной
логики переподключения — и `amqp-connection-manager` не нужен.

При завершении: отменить потребителя, дождаться завершения обработчиков в работе,
закрыть канал и соединение в `onApplicationShutdown`. Сообщения, оставшиеся
неподтверждёнными в момент падения, брокер доставит снова — это то же свойство,
что делает ретраи безопасными.

## 6. Топология развёртывания

- Сервис `rabbitmq` на образе `rabbitmq:4-management-alpine`, с healthcheck
  `rabbitmq-diagnostics -q ping` и именованным томом для данных. Панель управления
  публикуется наружу только в `docker-compose.single-api.yml`, где она нужна для
  разработки.
- Сервис `worker`: тот же образ, что и `api`, `command: node dist/worker/main.js`,
  `deploy: replicas: ${WORKER_REPLICAS:-2}`, `depends_on` на `postgres`, `rabbitmq`
  и одноразовый `migrate`. Портов не публикует. В режиме `lazy` штатно завершается
  сразу после старта (§5), поэтому его `restart` не должен перезапускать его в
  цикле.
- `stop_grace_period` у воркера выставлен так, чтобы обработчик успел завершиться.
- `api` получает `RABBITMQ_URL` и `RESERVATION_EXPIRY_MODE`; ни один порт API
  по-прежнему не публикуется — трафик идёт через nginx, как в под-проекте 3.

Ни `docker-compose.single-api.yml`, ни `apps/web/nginx.conf` в остальном не
меняются.

## 7. Конфигурация

Новые переменные в `apps/api/src/config/env.ts`. Все — со значениями по умолчанию,
кроме `RABBITMQ_URL`.

| Переменная                    | Тип и значение по умолчанию              | Смысл                                                       |
| ----------------------------- | ---------------------------------------- | ------------------------------------------------------------ |
| `RESERVATION_EXPIRY_MODE`     | `lazy` \| `queue`, по умолчанию `lazy`   | Подсистема не включает себя сама                             |
| `RABBITMQ_URL`                | url `amqp`/`amqps`, **без значения**     | Обязательна при `queue`; иначе процесс не стартует           |
| `RABBITMQ_PREFETCH`           | int 1…10 000, по умолчанию 20            | Неподтверждённых сообщений на канал                          |
| `RABBITMQ_PUBLISH_TIMEOUT_MS` | int 1…60 000, по умолчанию 200           | Порог, за которым медленный брокер считается недоступным     |
| `RABBITMQ_RETRY_DELAYS_MS`    | список int, по умолчанию `5000,30000,120000` | Ступени ретрая; длина списка задаёт число попыток        |

`RESERVATION_EXPIRY_MODE=queue` без `RABBITMQ_URL` — ошибка на старте, тем же
`refine`, что уже связывает `LOCK_STRATEGY` и `REDIS_URL`. Отсутствие значения по
умолчанию у `RABBITMQ_URL` — сознательное отклонение от таблицы `spec.md` §7 по
той же причине, что и у `REDIS_URL`: значение по умолчанию делает проверку
недостижимой.

Режим по умолчанию — `lazy`, и это принципиально: на этом коммите поведение
под-проекта 3 воспроизводится без единой новой сетевой операции, а измерения
остаются сравнимыми.

**`heartbeat` не выставляется в `0`.** В `amqplib` 2.0.0 ноль означает «отключить
heartbeat», а не «положиться на сервер»; чтобы взять значение сервера, параметр не
передаётся вовсе.

## 11. Definition of Done

- Истёкший холд переходит в `EXPIRED` доставленным сообщением, без участия
  чьего-либо запроса, и места возвращаются в пул.
- Тот же холд истекает и при остановленном брокере — ленивым путём, без ошибки у
  пользователя.
- Дубликат доставки не производит второго эффекта; подтверждённая бронь не
  отменяется сообщением, пришедшим по расписанию.
- Падающий обработчик проходит ограниченное число ретраев с возрастающей
  задержкой и заканчивает в DLQ; ядовитое сообщение попадает туда сразу.
- Разрыв соединения с брокером восстанавливается сам, с переобъявлением топологии.
- `RESERVATION_EXPIRY_MODE=lazy` на этом коммите ведёт себя как под-проект 3.
- `npm run lint && npm run typecheck && npm test` проходят; Playwright по-прежнему
  доходит от списка фильмов до подтверждённой брони через балансировщик.
- Нет outbox, нет `Idempotency-Key`, нет circuit breaker, нет rate limiting, нет
  Prometheus, нет Kafka, нет платежей. `amqplib` — единственная новая
  рантайм-зависимость, и `@types/amqplib` **не установлен**: типы идут в пакете.
- Девять ADR записаны, README обновлён.

## 12. Что этот под-проект оставляет следующему

- **Точка, где истечение становится событием.** Под-проект 5 подключит к тому же
  exchange платёжные сообщения; `cinema.commands` и `assertTopology` — то место,
  куда они добавляются.
- **Продюсер, публикующий после коммита без гарантии.** Это ровно тот шов, который
  закрывает транзакционный outbox, когда сообщение начнёт стоить денег.
- **Однородность TTL как записанное предусловие.** Если платёж удлинит холд,
  очередь ожидания придётся заменить: §3 говорит, чем и почему.
- **Fail open в двух местах.** Redis и брокер оба платят таймаутом на каждом
  запросе, пока лежат. Circuit breaker под-проекта 5 получает две подсистемы с
  одинаковой формой отказа и один общий абстрактный слой.
- **Глубина очередей и DLQ как первые метрики.** Под-проекту 10 есть что
  соскребать в первый же день: глубина `wait`, глубина `dlq`, распределение
  `x-attempt`.
